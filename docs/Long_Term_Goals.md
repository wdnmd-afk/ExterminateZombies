# ExterminateZombies 长期目标文档

## 1. 文档目的

本文档用于定义 `ExterminateZombies` 的长期建设方向，统一以下问题：

1. 这个项目最终要做成什么样。
2. 当前版本已经到哪里，还缺什么。
3. 后续迭代优先级如何排序。
4. 哪些内容属于长期目标，哪些内容暂时不做。
5. 在扩功能时，如何避免项目变成“功能很多但没有灵魂的半成品”。

本文档是对 [PLAN.md](/E:/github/ExterminateZombies/docs/PLAN.md) 的长期补充。
`PLAN.md` 解决“怎么把当前版本做出来”，本文档解决“这个项目长期要走到哪里”。
具体执行拆解请配合 [Long_Term_Roadmap.md](/E:/github/ExterminateZombies/docs/execution/Long_Term_Roadmap.md) 一起使用。

## 2. 项目北极星

### 2.1 一句话目标

做一款 **能在网页中快速打开、5 秒内进入战斗、15 分钟内形成明显爽感与策略反馈的漫画风俯视角打僵尸游戏**。

### 2.2 北极星体验

玩家进入游戏后，应该在极短时间内感受到以下几件事：

1. **枪有手感**：每次开火、命中、击杀、爆炸都清晰、有区分度。
2. **场景不是摆设**：油桶、面粉桶、地雷、地形布局都能改变战斗节奏。
3. **敌人不是换皮数字包**：不同僵尸会迫使玩家改变移动和开火方式。
4. **一局有递进感**：从能活下来，到会利用环境，再到追求更高分、更快通关、更远波次。
5. **视觉上有明确记忆点**：不是普通网页小游戏，而是有“漫画战报感”和“战场贴纸感”。

### 2.3 最终判断标准

长期来看，这个项目是否成功，不以“代码量”或“功能数量”为标准，而看以下三点：

1. 玩家能否在几分钟内理解玩法并感到反馈充足。
2. 玩家是否愿意重复开局，而不是打一局就丢。
3. 项目是否形成明确风格，而不是“技术上能跑但没有识别度”的作品。

## 3. 当前阶段判断

截至当前代码状态，项目已经跨过“纯技术脚手架”阶段，进入 **可玩原型 + 持续打磨阶段**。

已具备的基础能力：

1. Phaser + Vite + TypeScript 基础架构已经跑通。
2. 玩家移动、瞄准、开火、换弹、切枪链路已存在。
3. 僵尸追击、伤害、死亡、掉落已存在。
4. 场景物爆炸、连锁、残留区、地雷已存在。
5. 关卡模式、无尽模式、关卡解锁、设置改键已经接通。
6. HUD、波次提示、暂停覆盖层、基础战斗反馈已接通。

当前仍属于“未完成但已有明显形态”的阶段，主要短板在：

1. 玩法深度还不够，系统数量已经开始超过内容密度。
2. 美术仍以占位几何图形为主，漫画风格还没有真正成型。
3. 音效、正式粒子、节奏控制、难度曲线还没有经历完整打磨。
4. 缺少面向外部试玩的版本质量门槛与内容量。

结论：

- 当前不该再无节制扩系统。
- 未来中期重点应该转向 **内容生产、手感打磨、风格统一、版本质量门槛**。

## 4. 长期建设原则

### 4.1 玩法优先于功能堆砌

每新增一个系统，都必须回答：

1. 它是否真正改变玩家决策。
2. 它是否增强战斗层次，而不是只增加操作负担。
3. 它是否能被现有内容复用，而不是只服务一个孤立场景。

如果答案是否定的，就不做。

### 4.2 风格优先于素材数量

项目长期目标不是做“素材很多的网页射击游戏”，而是做“风格清晰、反馈统一”的作品。

宁可先用少量但统一的视觉元素，也不要杂乱拼贴不同来源的资源包。

### 4.3 数据驱动优先于硬编码

长期扩展必须继续坚持：

1. 武器从配置表扩展。
2. 僵尸从配置表扩展。
3. 关卡从配置表扩展。
4. 数值调整尽量不改逻辑层。

这不是为了“写得学术”，而是为了后续内容扩张时不失控。

### 4.4 短时爽感优先于复杂学习成本

这类网页游戏的长期价值，不来自复杂教程，而来自：

1. 快速开始。
2. 快速死亡但愿意重开。
3. 快速感受到自己比上一局更会打。

因此任何长期设计都应该优先支持：

- 明确反馈
- 快速重开
- 高可读性
- 高复玩性

### 4.5 项目边界必须清楚

长期目标可以大，但阶段边界必须严格。

例如：

1. 在线排行榜可以是后续版本目标，但不应影响当前单机闭环。
2. 联机对战可以在愿景中保留，但不应提前侵入当前架构。
3. 账号系统、云存档、多人模式都不应在核心玩法未稳定前介入。

## 5. 长期目标分层

## 5.1 产品层目标

### A. 做成“可长期重复游玩的单机网页动作游戏”

核心不是通一次关，而是形成至少三类重复游玩驱动力：

1. **通关驱动**：想解锁下一关。
2. **成绩驱动**：想刷新分数、波次、通关时间。
3. **玩法驱动**：想尝试不同武器、不同地形利用方式。

### B. 形成自己的内容节奏

长期版本中，每一关都不应只是“怪更多、数值更大”，而应该至少有一个独立记忆点：

1. 地形布局不同。
2. 场景道具分布不同。
3. 僵尸组合不同。
4. Boss 压迫感不同。
5. 关卡目标或节奏不同。

### C. 做成“短局但不浅”的结构

长期理想单局长度：

1. 关卡模式：8-15 分钟。
2. 无尽模式：5 分钟内进入压力区，15 分钟后明显进入高风险区。

这意味着：

1. 前期不能拖。
2. 中期要有节奏变化。
3. 后期要有明显资源与环境博弈。

## 5.2 玩法层目标

### A. 武器系统长期目标

长期武器设计不应只区分 DPS，而应区分战斗职责：

1. 手枪：稳定、可靠、默认武器。
2. 冲锋枪：近中距离压制与机动战。
3. 步枪：中远距离穿透与单体处理。
4. 霰弹枪：近距离清场与爆发。

中后续可增加但必须有明确角色的类型：

1. 点射式高精度武器。
2. 面伤类或投射类武器。
3. 带控制效果的特殊武器。
4. 资源稀缺但高收益的重火力。

### B. 僵尸系统长期目标

僵尸长期设计目标不是数量扩张，而是压迫方式扩张。

建议长期维度：

1. **追击型**：迫使玩家持续位移。
2. **高血量型**：迫使玩家切换火力分配。
3. **爆炸型**：迫使玩家保持距离和位置管理。
4. **控场型**：改变战场可走区域。
5. **远程型**：迫使玩家不只看近身包围。
6. **召唤型 / 指挥型**：形成战场优先级判断。

最终目标不是僵尸种类越多越好，而是每多一种，玩家就要多一种处理思路。

### C. 场景交互长期目标

长期来看，场景物应该成为核心战术层，而不是“偶尔可以炸一下”。

长期目标包括：

1. 爆炸物：油桶、燃料罐、车辆等。
2. 阻挡物：可摧毁或不可摧毁的掩体。
3. 控场物：粉尘、火焰、毒液、减速区。
4. 机关物：触发式陷阱、门、警报器、电网等。

理想状态：

玩家在看到场景布局时，会先想“怎么利用环境”，而不是只想着“站哪射更久”。

### D. 无尽模式长期目标

无尽模式不能只是“波次数字无限增长”。

长期需要具备：

1. 阶段性敌人池变化。
2. 阶段性资源稀缺/补给差异。
3. 特殊事件波次。
4. 小 Boss / 精英波机制。
5. 明显的风险升级点。

无尽模式的长期价值应在于“战场管理”和“极限资源决策”。

## 5.3 视觉与品牌层目标

### A. 漫画风必须从“点缀”升级成“整体语言”

长期目标不是在界面上加几个 `BOOM!` 文字，而是让整套表达统一：

1. HUD 像漫画战报。
2. 爆炸像漫画击框。
3. 菜单像海报封面。
4. 结算页像刊物封底。
5. 关卡提示像分镜切页。

### B. 建立固定视觉资产体系

长期需要形成统一资产规则：

1. 字体组合固定。
2. 警示色、强调色、背景色固定。
3. UI 边框与描边规律固定。
4. 粒子与特效的风格固定。
5. 文案气质固定。

只有这样，后面新增页面和效果时，整体才不会散。

### C. 角色与敌人最终不再使用几何占位

长期目标中，玩家、僵尸、Boss、武器和关键场景物应逐步替换为正式资源，但替换顺序必须克制：

1. 优先替换玩家和基础僵尸。
2. 再替换高频场景物和拾取物。
3. 最后替换 UI 细部和特殊敌人。

原则是：

先替换“玩家每秒都在看”的东西，再替换边缘元素。

## 5.4 技术与工程层目标

### A. 维持轻量、可部署、可继续扩展

长期技术目标：

1. 保持单机静态部署能力。
2. 保持 `npm run dev` 与 `npm run build` 成本低。
3. 保持主要玩法层在 `config + systems + scenes` 的清晰分层中演化。
4. 不因未来可能的联网需求提前污染当前核心结构。

### B. 建立版本级质量门槛

后续阶段至少应逐步建立：

1. `typecheck` 持续为 0 报错。
2. 关键玩法链路有最小回归测试。
3. 重要配置改动有可见验收清单。
4. 重大版本前有固定检查表。

### C. 预留但不提前做重系统

长期可以预留的方向：

1. 排行榜
2. 云存档
3. 成就系统
4. 挑战任务
5. 联机合作

但这些都应该在核心战斗和内容完成度达到一定标准后，再进入优先级列表。

## 6. 长期路线图

## 阶段 A：原型定型期

### 目标

把当前版本从“能玩”打磨到“值得继续做”。

### 核心任务

1. 完成基础手感、HUD、暂停、提示、结算体验。
2. 把前 3 关与无尽模式的基础循环打磨稳定。
3. 让武器、僵尸、场景物的差异足够明显。
4. 跑通核心数值平衡一轮。

### 阶段完成标准

1. 玩家第一次打开能完整打完一局。
2. 玩家能区分主要武器与主要敌人差异。
3. 不依赖解释文档，也能理解关卡与无尽玩法。
4. 至少存在一个让玩家愿意重开的理由。

## 阶段 B：垂直切片期

### 目标

做出一个可以代表最终品质方向的“高质量小版本”。

### 核心任务

1. 选 1-2 个关卡打磨到接近正式品质。
2. 替换关键角色与高频场景物的正式视觉资源。
3. 接入基础音效和更统一的特效风格。
4. 完成至少一个有记忆点的 Boss 战。

### 阶段完成标准

1. 有一小段内容能够完整体现项目特色。
2. 外部试玩者可以明确说出本游戏的记忆点。
3. 美术、UI、战斗反馈开始形成统一语言。

## 阶段 C：内容扩张期

### 目标

从一个垂直切片，扩展成真正可发布的内容量。

### 核心任务

1. 关卡数量扩展到可形成一轮完整流程。
2. 武器、僵尸、Boss、场景机关扩展到稳定池。
3. 无尽模式增加事件、精英、特殊波次。
4. 加入更明确的记录驱动与挑战驱动。

### 建议目标规模

1. 5-8 个正式关卡。
2. 6-10 类明确分工的敌人。
3. 6 把以上可区分战斗职责的武器。
4. 3 个以上有记忆点的 Boss。

### 阶段完成标准

1. 游戏不再依赖单一玩法维持新鲜感。
2. 重复游玩时，玩家能感受到不同战术选择。

## 阶段 D：公开试玩期

### 目标

把项目从“开发者自己觉得不错”推进到“外部玩家能给出有效反馈”。

### 核心任务

1. 做试玩版本说明与反馈收集入口。
2. 修复首次体验中的理解成本问题。
3. 调整教程缺失、节奏拖沓、视觉噪音等外部试玩最容易暴露的问题。
4. 建立版本迭代节奏。

### 阶段完成标准

1. 外部玩家能独立完成一局。
2. 外部反馈集中在“平衡和偏好”，而不是“看不懂/玩不明白/进不去”。

## 阶段 E：发布候选期

### 目标

准备首个可正式对外发布的版本。

### 核心任务

1. 完成正式菜单包装、结算包装、信息展示统一。
2. 完成最低限度的性能优化和兼容性处理。
3. 清理临时占位和明显粗糙区域。
4. 固定版本质量清单。

### 阶段完成标准

1. 项目在视觉、玩法、工程三方面都达到“可以拿出去”的下限。
2. 不是 Demo 拼盘，而是一个完整的小型作品。

## 7. 长期功能清单

以下是可以进入长期池的方向，但不代表全部都要做。

### 7.1 高优先级长期功能

1. 正式美术替换
2. 音效与音乐系统
3. 更丰富的武器差异
4. 更完整的 Boss 设计
5. 关卡目标差异化
6. 无尽模式事件系统
7. 记录驱动与挑战驱动

### 7.2 中优先级长期功能

1. 成就系统
2. 挑战关卡
3. 特殊环境机制
4. 额外难度模式
5. 简易教程引导

### 7.3 低优先级或远期功能

1. 在线排行榜
2. 云存档
3. 账号系统
4. 联机合作/联机对战

这些内容只有在单机核心体验已经稳定且内容量足够时，才值得进入实施阶段。

## 8. 明确非目标

以下内容在长期文档里可以保留为“未来可能”，但当前不应被视为主目标：

1. 做成大型开放世界。
2. 做成复杂叙事驱动 RPG。
3. 做成重数值成长的刷子游戏。
4. 做成多人在线服务型游戏。
5. 为了“看起来高级”而引入沉重后端和复杂账号体系。

项目的长期正确方向，是 **小而硬、短而爽、风格明确、可复玩**，不是无限膨胀。

---

## 9. 质量门槛

长期所有版本都应该逐步对齐以下门槛：

### 9.1 玩法门槛

1. 每个武器必须有清晰战斗身份。
2. 每个敌人必须有清晰压迫方式。
3. 每个关卡必须有清晰记忆点。
4. 每个新增系统必须改变玩家决策，而不是只改变数值表。

### 9.2 视觉门槛

1. 新增 UI 必须服从既有视觉语言。
2. 新增特效不能破坏整体风格统一。
3. 所有重要信息必须高可读。
4. 不允许堆叠无意义装饰。

### 9.3 工程门槛

1. 类型检查必须通过。
2. 不能用猜字段和兜底字段写法糊过去。
3. 配置与逻辑分层不能被随意打穿。
4. 非必要不引入新依赖。

## 10. 长期风险与防失控策略

### 风险 1：功能越做越多，但核心手感没打透

策略：

1. 每个阶段先问“手感是否明显提升”。
2. 如果没有，就不继续扩系统。

### 风险 2：资源来源过杂，视觉开始失控

策略：

1. 建立视觉风格白名单。
2. 替换资源时优先统一，而不是先追求丰富。

### 风险 3：无尽模式和关卡模式开始互相拖累

策略：

1. 保持两者共享基础系统。
2. 让节奏差异来自配置和规则，而不是两套平行代码。

### 风险 4：未来联网需求反向污染当前结构

策略：

1. 所有持久化继续收口到 `SaveManager`。
2. 后端相关需求不提前侵入核心战斗代码。

---

## 11. 文档维护建议

本文档不是一次性文件，建议按以下方式维护：

1. 每完成一个阶段，更新“当前阶段判断”。
2. 每次准备扩一个大系统前，先对照本文档看它属于哪个阶段、是否真有必要。
3. 如果项目方向发生明显变化，先改本文档，再改执行文档。
4. 如果某个目标已经证明不适合项目，应明确删掉，而不是留着占位置。

---

## 12. 最终结论

`ExterminateZombies` 的长期目标，不是做成“功能越来越多的网页小游戏”，而是做成一款：

1. 有清晰战斗手感
2. 有明确漫画风格
3. 有环境策略层
4. 有重复游玩价值
5. 轻量但完整

的小型高完成度作品。

如果后续所有新增内容都围绕这五点推进，项目会越来越清晰。
如果偏离这五点，项目就会越来越散。
