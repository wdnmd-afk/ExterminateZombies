# 2026-08-22 UI 勘察发现的问题修复

> 状态：已实施，已通过 Chrome 实机验收
> 起因：上一轮用生图 API 视角勘察 UI 时顺带发现的既有缺陷，与生成新素材无关
> 关联：`2026-08-22-weapon-topdown-sprites.md`（其溢色统计把 `portrait-watcher.png`
> 列为影响最大的两个文件之一，本轮修掉其中一个）、`docs/playDesign/角色与战前整备系统.md` §8.1（配色口径）

## 1. 本轮修了什么

四项，全部是既有缺陷，不含任何新素材生成：

| # | 问题 | 类型 |
| --- | --- | --- |
| 1 | `portrait-watcher.png` 过采样 4.2 倍 / 2.9MB，且带 2840 个键控残留像素，还不由任何脚本产出 | 资产 + 管线 |
| 2 | README 的武器数、编队槽位数、强化卡数与代码不符 | 文档漂移 |
| 3 | `GameOverScene` / `LevelClearScene` 是黑底上一列裸文字，无分组无层级 | 版式 |
| 4 | 暂停底板与三处次级按钮用米白实心，与全局配色口径是两套语言 | 配色 |

## 2. 修复 1：战前立绘的过采样与键控残留

### 2.1 两个叠在一起的缺陷

`src/assets/processed/characters/portrait-watcher.png` 是 2026-08-18 人手抠图后
**直接落到 processed 目录**的文件，不经任何脚本。因此同时存在三个问题：

1. **过采样。** `920 x 1933`，而战前整备页把它按
   `min(188 / w, 230 / h)` 塞进 `188 x 230` 展示区（`PreparationScene.updateCharacter`），
   相机 zoom 上限是 `DisplayManager.MAX_RENDER_SCALE = 2`，所以它最多只占
   **`219 x 460` 物理像素**——约 4.2 倍线性过采样，单文件 2.9MB 首屏带宽。
2. **键控残留。** 实测 2840 个可见洋红像素，含 alpha 255 的不透明边缘像素
   （样例 `(140, 6, 125)` 在 y=24 的主体上边缘）。这与 `sprite-watcher.png` 当年那
   128 个残留是同一类缺陷，`2026-08-22-weapon-topdown-sprites.md` 的溢色统计已经
   把它列为影响最大的两个文件之一并建议单独一轮处理。
3. **不可复现。** 没有脚本产出它，因此上面两条谁都拦不住，也没人能重跑。

### 2.2 处置

把它移到 `src/assets/generated/characters/Watcher_portrait_keyed.png` 当归档源，
运行时产物改由新分支派生：

```
python scripts/process_character_assets.py portrait-downsample watcher
```

分支做三件事，顺序不能换：

1. **先去色溢**，复用 `remove_magenta_background`（与感染体、图 B 同一套 BFS 判据）。
   必须在降采样之前：这些洋红在不透明像素上，LANCZOS 会把它们摊到邻居上，
   先降采样再去色溢等于先把污染抹开再擦。
2. **按预乘 alpha 降采样**到高 480。预乘是硬要求——归档图透明区的 RGB 仍是洋红
   `(250, 5, 246)`（键控只压了 alpha 没改 RGB），直接对 RGBA 做 LANCZOS 会把这些
   洋红按权重混进主体边缘，等于重新制造这条管线已经修过的紫边。
3. **门禁**：产物的可见洋红像素必须为 0，否则脚本退出非零。

目标高度取 480 而不是刚好够用的 460：与 Kenney 矢量分支栅格化后的 480
（`PreloadScene` 的 `PORTRAIT_BASE_SCALE 5` × 倍率 2 × 画幅 48）对齐，
两条分支源精度一致，将来五人换成 AI 立绘时不必再挑一个新数字。

### 2.3 刻意没做的两件事

1. **不从直出原图 `portrait-watcher-raw.png`（`2048 x 2048` RGB）重新键控。**
   那会连带改变边缘与去色溢结果，等于在"只解决体积"之外偷偷改观感；
   而且该直出图按 `CHARACTER_PORTRAIT_PROMPTS.md` §4.2 已因双脚缺失被淘汰。
   五人图 A 正式补齐时会走新管线整体重做，那时再从直出原图起算。
2. **不裁到主体。** 归档图带 24px 透明边距，裁掉会让人物在展示区从 224px 长到 230px。
   本轮只改分辨率，展示观感逐像素等价。

### 2.4 实测

| 项 | 修复前 | 修复后 |
| --- | ---: | ---: |
| 尺寸 | `920 x 1933` | `228 x 480` |
| 文件 | 2981 KB | 140 KB（**-95.3%**） |
| 可见洋红像素 | 2840 | **0** |
| 战前页展示尺寸 | `109.2 x 230.0` 逻辑像素 | `109.3 x 230.0` 逻辑像素（舍入差） |
| `vite build` 产物 | 3,052,368 字节 | 143,682 字节 |

## 4. 修复 3：结算页版式

### 4.1 原状的三个实际问题

两个结算场景都把全部统计塞进**一个居中的多行 Text**，再用 `fitTextBlock` 整体缩放
塞进标题与按钮之间：

1. 17 行统计在 720 高里被压到十几 px，全部居中对齐，没有任何分组或层级——
   想找"我打了多少击杀"要逐行扫。
2. `formatDuration` / `formatWeaponUsage` / `formatAmmoEconomy` 在两个文件里
   **逐字复制了两份**，改一处必然漏另一处。
3. 按钮用米白实心底板，与其它界面两套语言（见第 5 节）。

### 4.2 处置：抽出 `src/ui/debrief.ts`

两个场景近乎重复，因此把底板、标题、统计卡片网格、页脚行和按钮抽成共享构件，
场景只提供数据。三个格式化函数一并收敛到这里。

版式：

- **黑色战术台面 + 48px 细网格**，参数与 `MainMenuScene` 逐项相同，保证是同一张台面。
- **左侧强调色条**：失败暗红 `0xd32f2f`、通关绿 `0x388e3c`，与武器库的黄条、
  怪物图鉴的红条同一族标识。
- **12 张统计卡片，4 列 3 行**。每张是 `中文标签 // ENGLISH` + 大号数值，
  形态取自怪物图鉴档案页已有的 `生命 // HEALTH` 栅格。得分卡带黄色左缘条作为强调，
  不靠改底色——底色一变，网格节奏就散了。
- **两条页脚行**放会变长的内容（武器占比、弹药补给），超宽只缩该行。
- **按钮配色、描边、hover 上浮 2px、按下 0.985 缩放逐项对齐
  `MainMenuScene.createActionButton`**，不引入第二套按钮语言。

数据一项没删。原来挤在一行里的「环境: 油桶 4 / 粉尘 1 / 地雷 7」变成一张卡：
数值是合计 12，细分放卡内第二行。

差异化处理：

- `GameOverScene` 无尽模式在右上角第二行显示 `无尽最佳 W12`；关卡模式显示关卡名。
- `LevelClearScene` 有下一关时「下一关整备」是主按钮；无下一关时「返回主菜单」升为主按钮，
  提示语也从"进入下一关时归零"改成"本局结算后归零"。

新代码**不使用 `letterSpacing`**：它不在 Phaser 3.80.1 的 `TextStyle` 类型里，
仓库既有的 24 个类型错误全部来自它，不再新增同类。

## 5. 修复 4：米白底板配色

`docs/playDesign/角色与战前整备系统.md` §8.1 定的口径是
**黑色战术台面 + 旧纸白信息层 + 警戒黄操作焦点**。主菜单、武器库、怪物图鉴、
战前整备都遵守，但四处没有：

| 位置 | 原状 | 改为 |
| --- | --- | --- |
| `HUDScene` 暂停底板 | 整块米白 `0xf4eedd` @0.98 + 深色标题 | 黑台面 `0x0f0e13` @0.97 + 顶部警戒黄条 + 旧纸白标题 |
| `SettingsScene` 返回主菜单 | 米白实心 + 深色字 | 深底 `0x1d1d24` + 旧纸白字 + 半透明描边 |
| `CreditsScene` 返回主菜单 | 同上 | 同上，并补 hover 态（原来完全没有） |
| 两个结算页按钮 | 同上 | 走第 4 节的共享按钮 |

暂停底板这一处最明显：它压在战场上时会和**同为米白**的波次横幅叠成一片
（旧截图里 `WAVE 1` 横幅与 `PAUSED` 底板紧挨着，两块米白）。

**波次横幅本身没动。** 它是经 G6 波次节奏轮次验收过的战斗播报元素，米白闪烁是
故意的"盖章式"注意力抓取，且是瞬时淡出的；改它会动到战斗反馈手感，不属本轮范围。
设置页的滑块旋钮同理保留米白——那是控件把手，不是面板底色。

## 7. 本轮没做的

1. **感染体方向表的过采样，量级比立绘大 20 倍。** 修立绘时顺手量了全部运行时贴图：
   `src/assets/processed` 下 36 个 >300KB 的 PNG 合计 **65.3MB**，其中 14 张
   感染体方向表占约 48MB——`walker-directional-custom.png` 是 `4096 x 4096` / 15.8MB
   （`zombieVisuals.ts` 里 `frameWidth: 1024`），其余 13 张 `2048 x 2048` / 2-3.8MB
   （`frameWidth: 512`）。而感染体实机显示只有 28-86px，即单帧 512px 对约 40px 显示，
   **约 13 倍过采样**，walker 更是 28 倍。
   没有动的理由：改输出尺寸必须同步 `process_zombie_sprites.py` 与
   `zombieVisuals.ts` 的 `frameWidth/frameHeight`，14 张表 × 16 帧，
   一处不同步就是全体感染体动画错帧。属独立一轮，且要先定"单帧留多少倍余量"的口径。
2. **`walker-directional-custom.png` 的键控残留。**
   `2026-08-22-weapon-topdown-sprites.md` 点名的两个文件里，本轮只修了立绘那一个。
   walker 那张要连着第 1 条一起做才划算。
3. **战斗内波次横幅与滑块旋钮的米白**，理由见第 5 节末。
4. **结算页统计的取舍。** 12 张卡片是把原有数据重排，没有判断"哪些统计其实没人看"。
   如果试玩后觉得 12 项太多，删项比加项容易。
5. **上一轮列的 A/B 档生图项**（四人立绘、11 张军械档案图、9 张强化行为徽记、
   主菜单主视觉、10 张关卡简报图）一项未做——那些需要真实调用生图 API，
   且 4:5 能否直出仍待一次探针确认。
