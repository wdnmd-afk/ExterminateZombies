# Runner 感染体美术资源重整执行文档

> 建立日期：2026-08-20
> 
> 目标对象：`src/config/zombies.ts` 中的感染体 `runner`
> 
> 参考基线：`docs/execution/WALKER_SPRITE_PIPELINE.md`
> 
> 状态：资源与接线已完成，等待真人目视验收（见 §9.6）

## 1. 目标

将当前复用 Curt `31×36` 三帧方向表的 `runner`，重整为与 Walker 同等级的项目生成资源链：

1. 生成与 Walker 同画风、同机位、同键控底约束的 Runner 参考图。
2. 生成左、下、上三个方向的 `2×2` 四帧源图；右向由左向帧水平镜像，避免左右风格漂移。
3. 生成独立的 Runner 图鉴静态立绘，不从动画表截图放大。
4. 自动完成洋红键控、抗锯齿边缘去色、帧切分、主体居中和脚底基线对齐。
5. 产出 `4096×4096 RGBA` 四方向动画表与 `1024×1024 RGBA` 图鉴立绘。
6. 接入 Phaser 预加载、视觉布局、图鉴预览和资源台账；不改变 Runner 的生命、速度、冲刺能力、掉落和碰撞数值。

## 2. 范围

### 2.1 本轮包含

- 本地图片代理调用脚本：健康检查、参考图 Data URL、生成请求、结果下载和版本化命名。
- Runner 原始候选图保存到仓库根目录 `TmpGenerate/`。
- 采用后的源图归档到 `src/assets/generated/zombies/`。
- Runner 专用后处理脚本：键控抠图、2×2 切帧、镜像右向、尺寸/基线归一、方向表组装、图鉴图清理。
- `src/config/zombieVisuals.ts`、`src/scenes/PreloadScene.ts`、`src/scenes/MonsterLibraryScene.ts` 的运行时接线。
- `docs/RUNTIME_ASSET_MANIFEST.md`、`docs/ART_ASSET_REGISTRY.md` 与本执行文档的结果记录。

### 2.2 本轮不包含

- 修改 `runner` 的玩法配置、AI、冲刺前摇或数值。
- 修改其它感染体或可玩角色“疾行者”的素材。
- 生成攻击/死亡动作表；Runner 当前动作系统没有独立动作资源契约，本轮只替换移动与图鉴视觉。
- 运行生产构建、全量测试或浏览器验收，除非用户另行要求；本轮先完成静态与资源级核对。

## 3. 冻结规格

### 3.1 生成规格

- 风格：沿用 Walker 的暗色、粗颗粒、写实像素恐怖风格。
- 机位：正 90° 俯视，角色朝右；不画武器、地面、阴影、文字和水印。
- 键控底：纯洋红 `#FF00FF`，不得在主体中使用同色。
- 动画源：每张方向源图为 1:1 画布内的 `2×2` 四帧。
- 角色身份：新鲜、瘦削、前倾、弹簧式冲刺姿态；破旧连帽衫、跑鞋和明显伸展肌腱，轮廓必须区别于 Walker。
- 图鉴图：同一 Runner 身份、完整居中、单人静态姿态、1:1 画布。

### 3.2 实测环境约束（2026-08-20 实测，与原计划的偏差依据）

以下三项在执行中实测确认，直接改变了原计划的尺寸与验收方式：

| 约束 | 实测结论 | 对方案的影响 |
| --- | --- | --- |
| 上游输出尺寸 | `gpt-image-2` 恒定返回 `1254×1254`；`size: 2048x2048` 与 `imageSize: 2K` 均被忽略 | `2×2` 源图单帧仅 `627×627`，无法支撑 Walker 的 `1024` 帧规格 |
| 上游内容审核 | 含 `zombie`、`corpse`、`undead creature` 的提示词稳定返回 `502 upstream_generation_failed`；改为 `game enemy sprite` + `fast infected humanoid` + `gaunt grey-green skin` 后通过 | 提示词 6.2 原文不可直接用，需保留视觉语义的等价改写，并配置降级词表 |
| 本机图片查看 | 当前会话的图片读取工具对任何 PNG/JPG 均无返回 | 无法人工目检候选；改为量化指标门控 + 明确移交真人目视验收 |

### 3.3 运行时规格（按 3.2 修订）

- 方向表：`2048×2048`，4 行 × 4 列，每帧 `512×512`。
  - 修订原因：源单帧 `627`，降采样到 `512` 内的主体（约 `435px`）全程无放大；若沿用 Walker 的 `1024` 帧则需把 `627` 上采样 1.64 倍，纯属劣化。
  - 运行时 Runner 可见高度约 `47px`，`435px` 的源精度已远超需要，不损失任何实机可见细节。
- 行顺序：`down`、`left`、`right`、`up`（与 Walker 一致）。
- 动画帧率：`10 FPS`（Runner 速度 52 对 Walker 22，四帧循环需更快的步频）。
- 显示缩放：按 Walker 已验收比例反推。Walker 可见高约 `59px` / 半径 `14` = `4.21px per radius`；Runner 半径 `11` → 目标可见高约 `47px`，对应 `scale = 47 / 435 ≈ 0.108`。不改 `zombies.runner` 的碰撞半径。
- 图鉴图：`512×512 RGBA`，独立纹理 key，不复用动画表。图鉴预览缩放由 `resolveMonsterPreviewScale` 按帧尺寸自适应夹取，无需手改场景常量。

## 4. 操作步骤

1. 检查本地代理健康状态；若未运行，启动 `npm run image-api`，只监听 `127.0.0.1`。
2. 读取 Walker 参考图与提示词，构造 Runner 的统一提示词集；每个请求携带 Walker 参考图 Data URL，锁定风格与机位。
3. 依次生成并下载以下候选到 `TmpGenerate/`，不覆盖已有文件：
   - `zombie-runner-direction-reference-vNN.png`
   - `zombie-runner-left-4-vNN.png`
   - `zombie-runner-down-4-vNN.png`
   - `zombie-runner-up-4-vNN.png`
   - `zombie-runner-portrait-vNN.png`
4. 对候选做尺寸、键控底占比、主体边界和完整性检查；失败候选保留并递增版本号，不覆盖。
5. 将采用候选复制到 `src/assets/generated/zombies/` 的稳定命名，运行自动后处理脚本生成正式 PNG。
6. 更新视觉配置和预加载引用，图鉴对 `runner` 使用独立肖像纹理。
7. 做 V0 静态检查：引用链、纹理尺寸、PNG RGBA、方向行映射、无旧 Runner 纹理引用、玩法字段未改。
8. 记录生成请求、采用版本、处理参数和未验证项。

## 5. 实施建议

- 生成请求使用 Walker 方向参考图作为风格参考，不把 Walker 作为身份复制目标；提示词明确“只继承画风、像素密度和光源，不复制人物服装/伤口”。
- 右向严格由左向水平镜像；这样不会引入第二套模型生成的左右差异。
- 后处理只允许对洋红底做键控和边缘去色，不做自动锐化、重绘或内容修补，避免改变生成角色。
- 以每帧可见主体边界计算统一缩放和脚底基线；如果某一帧缺脚或严重漂移，整组候选判废，不单帧修补。
- 正式代码只引用 `src/assets/processed/zombies/`，不引用 `TmpGenerate/`。

## 6. 潜在风险分析

| 风险 | 影响 | 处理方式 |
| --- | --- | --- |
| 生图接口未配置或上游超时 | 无法得到候选图 | 先 `/api/health`，按代理返回的错误码停止，不高速重试 |
| 生成图四帧身份漂移 | 动画闪烁、Runner 变形 | 同一参考图、同一提示词骨架；逐帧边界检查，整组淘汰 |
| 洋红抗锯齿残边 | 深色战场出现紫边 | 通道差值键控 + 去色溢；检查透明角和边缘采样 |
| 方向源尺寸不一致 | Phaser 帧错位 | 后处理统一到固定正方形，再组装方向表 |
| Runner 视觉高度改变 | 与碰撞圆不匹配 | 只调整 `ZombieVisual.scale`，不改 `zombies.runner` 的玩法半径；需静态记录反推结果 |
| 图鉴仍显示旧三帧 | 资产替换不完整 | 单独登记 `runner` 肖像 key，并核对 `MonsterLibraryScene` 分支 |
| 生成内容含武器/阴影/文字 | 破坏运行时分层 | 提示词负面约束 + 候选验收，失败不进入正式目录 |

## 7. 优化方案

1. 只向代理发送必要的 Walker 参考图和单个请求，避免重复上传无关素材。
2. 将生成、下载、后处理拆成可重复脚本；任何一步失败都能从已有 `TmpGenerate/` 候选继续，不重复消耗生成额度。
3. 使用稳定版本号和哈希记录，保留未采用候选，便于回退和比较。
4. 把 Runner 的视觉布局数据继续集中在 `zombieVisuals.ts`，不把尺寸常量散落到场景代码。

### 9.4 键控缺陷修复

首轮产物在主体边缘残留 4177 个 `alpha>=96` 的洋红倾向像素，深色战场上会表现为紫边。根因是去色溢挂在 `alpha < 250` 条件下：约 25% 洋红混合的边缘像素 chroma 仅约 49，算出的 alpha 高达 251，整批跳过去色溢，但肉眼仍是明显紫色。

修复方式改为按空间距离限制作用范围——从已键出背景做 BFS 得到 `DESPILL_BAND = 3` 的边缘带，只在带内按洋红超出量压低 R、B，强度随距离衰减。这样既清掉污染，又不动主体内部合法的灰紫色阴影（如 `(154,129,157)`，绿通道明显不为 0）。

| 状态 | 边缘残留（alpha≥96） | 内部合法紫调保留 |
| --- | --- | --- |
| 修复前 | 4177 | 516 |
| 修复后（BAND=3） | 8（方向表）/ 0（立绘） | 280 |

带宽实测对比后确定保留 3：`BAND=6` 只把边缘残留从 11 降到 8，却把内部保留像素从 102 砍到 53，属于用合法配色换取无意义收益。剩余 8 个像素为孤立单点（其中 4 个是镜像重复，实为 5 处），在 `435px → 46.5px` 的 9.3 倍降采样下不可见。

### 9.6 返工记录：四方向画成同一朝向

用户实机反馈"上面三行都是向下的，根本没有左右"。属实，v04 与随后的 v06 都是废品，最终采用 v05 全套。

**根因两条叠加：**

1. `FRAMING` 段里写了 `clearly taller than wide`。这条比例硬约束压过了每个方向请求各自的朝向指令，模型四个方向都画成同一个直立姿态。比例本该由后处理归一化负责，提示词不该管。
2. 身份参考图是单个朝右姿态，却作为 I2I 参考传给每个方向请求，持续强化同一朝向。Walker 的 `Walker_direction_reference.png` 是四方向转身图，这才是管线原意。

**为什么第一轮检视没发现：** 当时通过的全部指标都测不出朝向错误。方向间轮廓 IoU 0.54–0.70 的差异只反映跑步循环里的姿态变化。后来补的自镜像对称度同样不可靠——冲刺时一臂前一臂后，正面视图本身就左右不对称（v05 left 实测 0.315），会被误判成侧面。

**有效判据是行间归一化轮廓 IoU**（按外接框裁出、缩放到同尺寸后只比形状）：

| 行对比 | Walker 已验收 | v04/v06（废） | v05（采用） |
| --- | --- | --- | --- |
| down vs left | 0.411 | 0.717 | 0.364 |
| down vs up | 0.697 | 0.656 | 0.623 |
| left vs up | 0.397 | 0.625 | 0.423 |

Walker 的特征是 `left` 明显远离 `down`/`up`，而 `down`/`up` 同为对称视图故彼此更近。v04/v06 三个数值全在 0.62–0.72，没有任何朝向分离。

已新增 `scripts/verify_directional_sheet.py` 作为方向表成品的常设门控，并用"三行都填 down"的人工缺陷样本验证过它会以退出码 1 拦下。

**同时修掉的两个连带缺陷：**

1. 归一化原为逐方向各自 box-fit。侧向帧是横躺的（宽高比 1.50），各自铺满自己的框会破坏方向间相对比例，角色转向时忽大忽小。已改为全 12 帧共用一个缩放系数（实测 0.7740）。
2. 原为脚底基线对齐。真正的俯视没有脚踩地面的基线，侧向帧高度远小于正面帧，底部对齐会让角色转向时上下跳动。已改为几何居中，并把 `runner` 的 `originY` 从 `0.62` 改为 `0.5`，原点即主体质心。
3. `validate_frame` 原按"高度 ≥ 0.6×帧高"判完整性，会把合法的横躺侧向帧判废。已改用较长边加非透明面积占比，不再预设角色竖直。

用 CDP 驱动真实渲染抓取证据。Playwright 未安装且安装需单独授权，本轮全程用仓库既有的 CDP 方式，脚本 `.debug-runner-direction-capture.mjs`，证据目录 `.debug-runner-direction-evidence/`（两者均在 `.gitignore` 内）。

**实机运行时状态（52–59 FPS，无控制台错误）：**

| 项 | 结果 |
| --- | --- |
| 方向表纹理 | `2048×2048`，17 帧（16 + `__BASE`），NEAREST |
| 四方向动画 | 各 4 帧、`10 FPS`，帧名确认行映射 `down=0 / left=1 / right=2 / up=3` |
| 实机精灵 | `scale 0.112`，显示 `57.3×57.3`，`originY 0.5` |
| 四只探针钉位后 | `facing` 与动画键与预期方向逐一吻合，帧号在推进 |
| 图鉴预览 | 纹理 `game-zombie-runner-portrait`、帧 `__BASE`、缩放 `0.2464`，边界在安全框内 |

**抓取过程中排掉的三个环境陷阱，后续做浏览器验收会再碰到，记录如下：**

1. **窗口被遮挡会让整个验证失效。** 窗口不可见时 `document.hidden` 为 `true`，Phaser 的可见性处理直接 `scene.pause()`，Chrome 同时把帧率限到 2–14 FPS。后果是生成缩放 tween 完全不推进，抓到的精灵永远停在起始的 `0.6` 倍大小（`0.112×0.6=0.0672`，即 34.4px），动画也卡在第 0 帧——很容易被误判成"素材尺寸错了"或"动画没做出来"。`Page.bringToFront` 不足以解决，必须用 `Emulation.setFocusEmulationEnabled {enabled:true}` 加 `Page.setWebLifecycleState {state:'active'}`；实测生效后 `hidden:false`、`scenePaused:false`、59 FPS。抓取脚本应在导航后立刻断言 `document.hidden === false`，不满足就停下报错，而不是继续抓无效证据。
2. **从控制台单次写入朝向会被 AI 下一帧覆盖。** 感染体 AI 在 `scene.update` 里每帧把速度改向玩家，`updateFacing` 随即改回动画行。实测出现过 `dir=down` 的那只显示 `right` 行动画。可靠做法是在 `scene.events.on('postupdate', ...)` 挂钩子每帧钉住位置与朝向，且只在动画键不同时才 `play`（否则每帧 `play(..., true)` 会把动画一直重置回第 0 帧，看起来像静止）。钩子需要几帧才压过 AI，截图前必须轮询等到四只的动画键全部对上。
3. **`Page.captureScreenshot` 可能返回缓存帧。** 连续两次抓取得到字节完全一致的 PNG，尽管其间运行时读到的帧号已经变化。判断"动画是否在推进"要靠运行时帧号，不能靠比对两张截图。

**另外两条与本次结论相关的限制：**

- 世界坐标必须落在相机可见范围内。最初把四只放在世界 `x=260/520/780/1040`，对比放置前后的截图只找到 2 个差异簇，说明两侧的两只在视口外。已改为 `430/530/630/730`。
- 用"隐藏/显示探针再差分"定位截图里的四只没有成功：差异簇面积只有 16–53px 且 y 坐标分散，实际抓到的是场上其它移动中的感染体。屏幕坐标换算还需要考虑逻辑画布与 canvas 的渲染倍率（canvas `3040×1440`，CSS `1280×606`），本轮没有做对。因此"四只是否都进了可见视口"这一条未被证明。

### 9.8 未验证项与已知风险

以下必须由真人确认，本轮无法覆盖：

1. **每一行画的是不是它该画的那个方向**。新门控只能证明四行朝向"彼此不同"且形态符合"侧向横躺、正背面竖向"，无法证明 `left` 行画的是朝左而不是朝右、`up` 行是背面而不是正面。这一点必须目视，看 §9.7 产出的 `row-*.png`。本会话的图片读取工具对任何 PNG/JPG、任何尺寸均无返回，我一张图都没看过；CDP 抓图只是把证据落到磁盘，不等于我看过它们。
2. **美术内容本身**。四帧是否构成自然跑步循环、`up` 是否真的没画脸、角色是否具备"快速、前倾、危险"的识别度、是否与 Walker 存在轮廓混淆。
3. **机位与 Walker 的风格差异**。Runner 侧向宽高比 1.50（真正的 90° 俯视，身体横躺），Walker 侧向是 0.64–0.76（身体竖立，实际是高角度俯视）。两者机位不完全统一，同场景并列时可能违和。我上一轮曾为对齐 Walker 而改动 left，结果把唯一正确的侧向图换成了正面——所以这次保留了真侧向，把机位统一留给你决定：若要 Runner 迁就 Walker，需要重做 left 且必须用 `verify_directional_sheet.py` 复核朝向没有丢。
4. **视觉体型变化**。Runner 实机可见尺寸由旧 Curt 素材的约 `33px` 变为最大 `48.7px`。按 Walker 已验收比例反推（可见/半径比值 4.429 对 4.449），落在规范的普通感染体 `28–48px` 区间上沿，但会让 Runner 成为更大的目标，战斗手感需你确认。
5. **`originY` 由 0.62 改为 0.5** 会让 Runner 精灵相对碰撞圆上移约 6px。几何上更正确（原点即质心），但与其它感染体的原点约定不同，需实机确认命中感。
6. **V4/V5 未执行**：未做四方向移动的实机播放观察、冲刺前摇表现和无尽模式压力场景。
