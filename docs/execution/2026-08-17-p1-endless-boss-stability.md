# 2026-08-17 P1 无尽首 Boss 稳定性执行文档

## 1. 目标

定位无尽模式在第 7～9 波提前 Game Over 的真实原因，优先修复战斗流程、状态或对象生命周期问题，使首个无尽 Boss（第 10 波 `tank_boss`）可被稳定到达并完成。未确认根因前不调整伤害、掉率、弹药或音量数值。

## 2. 范围

- `WaveManager` 的无尽波次生成、分段进度和 Boss 插入。
- `GameScene` 的伤害入口、Game Over、敌人投射物和区域爆炸生命周期。
- 只读诊断接口及长流程证据脚本。
- P1 发现逻辑缺陷时的最小修复与回归测试。

不在本阶段实现 G2-7，不修改正式数值，不引入依赖，不用测试存档或无敌注入证明正式经济链路。

## 3. 操作步骤

1. 读取现有无尽失败报告，按波次、生命、武器、弹药和活动敌人对齐失败时间点。
2. 增加有限长度的运行时诊断快照：波次管理器状态、活动对象数量、玩家生命、最近受伤事件、投射物和区域爆炸数量。
3. 在每个玩家伤害入口标记来源（近战、投射物、区域爆炸、持续火焰），并在 Game Over 前保留最后一段环形记录。
4. 用 Chrome CDP 运行至少两条独立无尽路线，缩短采样间隔，定位第 7～9 波失败根因。
5. 若确认流程/状态错误，实施最小修复并补纯规则或生命周期回归；若证据只指向正式平衡问题，则记录为待产品决策，不在本阶段擅改数值。
6. 通过定向测试、全量测试、类型检查、构建和长流程实景验证。

## 4. 实施建议

- 诊断数据不进入 HUD，不改变正式存档结构；通过 GameScene 只读方法供 CDP 探针读取。
- 环形记录限制条目数和字段，避免长局造成内存增长。
- `WaveManager.getProgressSnapshot()` 作为波次唯一事实来源，禁止在探针中复制波次推导。
- 伤害记录必须在 `Player.takeDamage` 确认实际扣血后写入，避免把无敌帧拦截误报为伤害。

## 5. 潜在风险

- 诊断回调若直接触碰已销毁场景对象，可能复现 P0 类生命周期异常；所有读取需允许对象为空。
- 过密采样会放大 CDP 驱动开销，采样周期应与证据需求匹配并在长流程后关闭。
- 发现的确是数值压力时，自动改数值会掩盖设计决策；必须保留原始证据并单独提出调整。

## 6. 优化方案

- 诊断记录使用固定上限环形队列，GameScene 重建时清空。
- 将伤害来源限定为已确认的四类枚举，禁止猜测字段或多字段兜底。
- 证据 JSON 同时保存失败前 10 秒的高频样本和最终快照，便于比较不同武器路线。

## 7. 验证方式

- 单元：诊断环形队列、伤害来源记录和缺失对象安全读取。
- 工程：`npm test`、`npm run typecheck`、`npm run build`。
- 实景：Chrome 1280×720、DPR 1，默认 `TESTING_FLAGS`，至少两次无尽长流程；目标是到达并完成第 10 波 `tank_boss`，或给出可复现的非代码平衡结论。

### 8.5 根因与处理决定

1. `WaveManager` 没有在第 7～9 波提前结束；路线 B 已真实穿过该区间，并由第 10 波固定插入 `tank_boss`。
2. 路线 A 的 `120` 点入射伤害与 `barrel_oil.effect.damage` 唯一对应；第 3 波不可能出现同为 `120` 点的 `bomber_boss` 死亡爆炸。旧路线“最后采样满血、随后数百毫秒至数秒 Game Over”的现象由终局诊断补齐为环境一击致死，而不是生命状态丢失。
3. 油桶会伤害玩家是既有设计，`120` 点是否应允许满血一击属于难度/平衡决策。按本阶段边界不修改正式伤害、半径或玩家生命；需产品决定后另立数值任务。
4. 本轮生产代码只保留诊断能力，没有为通过测试注入无敌、跳波或修改正式经济。

### 8.6 剩余限制

- 路线 B 证明首 Boss 可到达并击杀，但只覆盖一次随机样本，不能替代真人对难度是否公平的 V6 结论。
- 两条路线通过隔离测试存档选择已解锁初始武器，只证明战斗流程；不证明正式解锁、掉落或新存档经济。
- 是否降低油桶自伤、改为非致死下限或增加更明确的危险提示，需要产品确认，不能从本轮客观证据自动推出。
