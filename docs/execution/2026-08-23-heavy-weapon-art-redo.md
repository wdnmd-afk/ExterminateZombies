## 1. 问题

用户报告「加特林那些都不够好」。这是同一个缺陷的**第三次**回报：

1. 最初 `process_heavy_weapon_assets.ps1` 用 GDI+ 图元现画，加特林是黑箱子加横线、
   金色 M249 是一团金色色块。
2. 2026-08-22 改用 `process_heavy_weapon_profiles.py`，部件切得更细，但仍然是程序化色块。

程序化路线的上限就在这里，两个原因叠加：

- **侧视图标要与另外八张并排。** 那八张裁自 CC0 真实像素美术素材包，有手绘的材质、
  锈迹、螺钉与非线性明暗。程序化图元画不出这些，摆在同一个 HUD 军械槽里差距刺眼，
  而武器库预览按 2.35 倍放大显示，那里最明显。
- **俯视图的明暗模型对重武器不成立。** 原模型是一层**全局**后处理：填完所有部件后按列
  把最顶 2 行提亮、最底 2 行压暗，隐含假设是「整把枪是一个圆柱体」。手枪、MP5 近似成立，
  重武器不成立——加特林的机匣、转子、枪管束是三个直径完全不同的体，全局明暗只给整体
  轮廓的最外两行上色，**内部所有部件边界都没有明暗差**，整把枪读成一块被刻了几道线的平板。

此外三把枪的**机制签名**在贴图上都读不出来：加特林的 1200ms 预热（`spinUp`）、
M249 的十发一次弹链齐射（`ammoChain`）、喷火器的 250 短射程加燃烧区（`impactLinger`）。
两把机枪在缩略图尺寸下几乎只是「长短差不多的两根管子」。

## 3. 侧视图标：改走 AI 生图管线

程序化画不出手绘质感，那就不要再画——改成生成，并沿用角色 / 感染体管线已经验证过的
三段式：生成候选 → 可复算判据检视 → 键控降采样落地。

| 文件 | 职责 |
| --- | --- |
| `scripts/weapon_side_specs.json` | 三把枪的身份阶梯、轮廓描述、负面词表与全部阈值 |
| `scripts/generate_weapon_assets.mjs` | 出候选到 `TmpGenerate/`，不覆盖已有文件 |
| `scripts/inspect_weapon_side_candidates.py` | 五项判据检视，不达标非零退出 |
| `scripts/process_weapon_side_assets.py` | 键控 → 中和残留 → 预乘降采样 → 落 132x48 |

### 3.1 为什么侧视枪可以生图，而俯视图仍然不行

`generate_character_assets.mjs` 第 18 行记录过：模型会**无视**「正俯视」要求，
2026-08-18 的守望者图就是这么画成斜视图的。那条教训在这里不适用——侧视枪是上游训练
分布里最密的构图之一，机位根本不需要争。实测三把枪六张图**全部在措辞阶梯 0 一次通过**，
没有用到任何降级词表。俯视图仍由 `process_weapon_topdown_assets.py` 程序化生成，
因为那个视角的素材上游给不出来。

### 3.2 检视判据（按各自要抓的缺陷）

| 判据 | 抓什么 | 实测值 |
| --- | --- | --- |
| `aspect` | 画成竖着的枪 / 画成方块 | 2.41 / 2.60 / 3.30，逐把区间内 |
| `fill` | 枪画小了或画成实心方块 | 0.551 / 0.422 / 0.427 |
| `facingBias` | **画反了** | 2.12 / 1.55 / 2.19，下限 1.08 |
| `residue` | 洋红键控没抠净 | 见 §3.3 |
| `components` | 画了一整个军械架 | 全部 1 个连通域 |

`facingBias` 是其中最重要的一条。运行时不翻转这套贴图（`HUDScene`、`PreparationScene`、
`Pickup` 都是直接 `setTexture` 后等比缩放），画反了就是画反了；而「哪边是枪口」在一张
陌生的枪图上并不总是一眼可辨。判据本身是几何事实：机匣、弹箱、燃料罐都在后半，
枪管在前半，所以朝右的枪必然左重右轻。

### 3.3 洋红残留判据必须分两级（本轮修正的一个错误）

第一版把残留门槛写成绝对像素数 24，沿用的是 sprite-watcher.png 那 164 个紫描边像素的
量级（`2026-08-21-weapon-grip-alignment.md` §2 第 3 条）。结果加特林候选实测 243、
喷火器 88，全部被判不采用——**而这两张图是好的**。

原因是同一个像素数在两个分辨率下含义完全不同：sprite-watcher 的 164 个在 **48x48 成品**
里占 7%，肉眼明显；这里的 243 个在 **1254² 源图**里占 0.02%，降采样后完全消失。
一个共用的绝对门槛必然在一头误报、另一头漏报。

改成两级，并顺手查清了那些像素的来源（86% 不在透明区附近，是被金属包住的深色缝隙——
加特林枪管之间、机匣面板线里，键控自带的去色溢只作用于「紧邻已键出背景」的像素，
够不到那里）：

- `sourceResidueRatioMax` 0.004：候选级预警，按占主体不透明面积的比例算；
- `productResidueMax` 12：**成品级硬门控**，在 132x48 产物上数绝对像素数，
  这才是与那 164 个可比的口径。实测成品残留 1 / 0 / 5 像素。
- 后处理新增 `neutralize_residual_magenta`，把命中像素无条件钳回中性。
  三把枪的配色里没有任何合法的紫，所以不需要按位置限制；亮蓝色的点火焰不会被误伤
  （蓝高红低，判据里的 `floor - green` 为负）。

### 3.4 降采样必须先预乘 alpha

`golden_m249` 的候选是上游直接返回的带 alpha 图（**不是**洋红底，管线会自动判别），
透明区 RGB 是纯黑。直接对非预乘 RGBA 做 `resize`，PIL 会把透明像素的黑按同样权重算进
边缘，产出一圈深色脏边——在 HUD 的浅色槽位上尤其明显。预乘后透明像素贡献为 0，缩完再还原。

## 4. 俯视贴图：明暗模型与三个新图元

### 4.1 `perPart` 明暗模型

`scripts/lib_weapon_draw.py` 新增第二套明暗模型，由 spec 根上的 `shadeModel` 选择：

- `rim`（默认，原有行为）：整体最外两行渐变。
- `perPart`（俯视管线在用）：每个部件按**自己那一列**的上下边界算柱面明暗
  （顶亮、约四成处本色、底暗），再叠一层强度只有 0.22 的整体轮缘。

相邻部件因此天然出现明度断差，各自读成独立的体。这不是风格化：俯视图里枪管、燃料罐、
转子都是横放的圆柱，光从画面左上来时照亮的正是 -y 那一侧，沿 y 做柱面渐变是这个视角
下的物理结果。另给 `dome`（球胖的燃料罐）与 `flat`（真正的平面盖板、警示条、火焰）两种剖面。

新模型只对显式声明 `shadeModel: "perPart"` 的 spec 生效，**侧视管线的产物逐字节不变**
（§6 第 2 条已实测）。

### 4.2 三个新图元，各对应一把枪的机制签名

| 图元 | 替代了什么 | 为什么必须换 |
| --- | --- | --- |
| `barrels` | 用 `ribs` 在一根粗管上画竖线 | 竖线读作「刻了几道线」，读不出「枪管会转」。新图元先铺暗底再逐根画管，管间留出暗缝，枪管才可数——这是加特林 1200ms 预热的外形依据 |
| `belt` | 无 | 露出来的黄铜弹链。M249 的 `ammoChain` 签名，也是它在缩略图尺寸下与加特林唯一可区分的特征 |
| `hose` | 用 `box` 画一条直带 | 直线读作「又一根枪管」，中段按 `sag` 外凸才读作软管。且必须**排在部件列表最前**，两端被燃料罐与喷杆压住——第一版排在最后，两个端头露在外面，整根管子读作枪身下方浮着的一道暗色弧线 |

另加 `glow`（自发光点火焰，径向过渡）与 `rivets`（1px 铆钉，给大片钢面一个尺度参照）。

### 4.3 两处按实机效果回退的取舍

- **管数取 5 而不是真实 GAU-8 的 7。** 正俯视只看得到枪管环的上半，5 根在 21px 束高里
  每根还有 4px 净宽，降到实机 0.5 缩放后仍能分辨；7 根挤成 3px 一根，缝先糊掉。
- **M249 不画两脚架。** 收起的脚架在正俯视下是贴着枪管两侧的两条细线，实测读作
  「枪管外面套了个方框」；改成枪管前段一圈卡箍，读作「有东西夹在枪管上」。
- **M249 供弹机盖用带柱面明暗的 `taper`，不用平涂亮金 `box`。** 后者盖在机匣柱面高光
  该出现的那几行上，把整块机匣压回平的，读作机匣上贴了一条黄色塑料。抬起的面板要有
  自己的体积，就得有自己的明暗剖面。

## 5. 两条侧视管线写同一批文件（本轮踩到的坑）

`process_heavy_weapon_profiles.py` 与新的 AI 管线写的是同样三个文件。本轮实测：为验证
重构未改行为而重跑前者，**它静默把刚生成的 AI 图标覆盖回了程序化版本**。

已加显式守卫：不带 `--force` 只打印停用提示并退出，不动文件。彻底的解法是删掉那条管线
（仓库对上一版 `.ps1` 就是这么做的，理由见 `2026-08-22-weapon-topdown-sprites.md`），
但那是另一条会话刚提交的产出，留给用户决定。
