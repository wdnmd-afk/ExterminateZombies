# HUD 视口支持范围收缩执行文档

> 建立日期：2026-08-18
> 所属层级：`docs/execution/` — 实施与追踪
> 上游规划：`docs/playDesign/侧栏HUD空间利用.md`
> 事实来源：`src/ui/displayLayout.ts`、`src/scenes/HUDScene.ts`、`tests/display-layout.test.ts`

---

## 1. 目标

用户 2026-08-18 明确要求：**不兼容极端屏幕，只兼容正常屏幕**，并确认「正常屏幕」只指 16:9 / 16:10，同时确认取消微型侧栏形态。据此本轮完成三件事：

1. 取消微型侧栏形态，`MIN_HUD_SIDEBAR_WIDTH` 从 `50` 提到 `120`：侧栏宽度不足 120px 时直接回退战场内 HUD，不再经过只剩图标的中间形态。
2. 在规划文档中确立**支持视口范围**，把「哪些屏幕保证、哪些不保证」写成明确结论，替代原先散落在风险条目里的暗示。
3. 清理由第 1 项连带产生的死值与失效断言，保持代码、文档、测试三方一致。

## 2. 已确认的屏幕落点事实

本轮所有决策都基于下表（按 `resolveDisplayLayout()` 实际公式演算，非估算）：

| 屏幕 | 宽高比 | `sidebarWidth` | 改动前档位 | 改动后档位 |
| --- | ---: | ---: | --- | --- |
| 1920×1080 / 2560×1440 / 3840×2160 | 1.78 | 0 | C | C |
| 1920×1200 / 2560×1600 | 1.60 | 0 | C | C |
| 2560×1080 | 2.37 | 214 | B 宽压缩 | B 宽压缩 |
| 3440×1440 | 2.39 | 220 | B 宽压缩 | B 宽压缩 |
| 3840×1600 | 2.40 | 224 | B 宽压缩 | B 宽压缩 |
| 5120×1440 / 3840×1080 | 3.56 | 640 | A | A |

两条关键推论：

1. **全部 16:9 / 16:10 屏幕的 `sidebarWidth` 都是 0。** 因此「正常屏幕」一律走 C 档战场内 HUD，侧栏 HUD 实际只服务 21:9 及更宽的屏幕。这是本轮范围界定的依据，也必须在规划文档里写明，避免后续误以为侧栏是主形态。
2. **A 档门槛是宽高比 ≥ 2.500**，恰好落在 21:9（2.37–2.40）与 32:9（3.56）之间的空隙，市面上没有该比例的显示器。因此 A 档现实中只有 32:9 能进入。

本轮**不调整** A / B 档阈值：用户已表态正常屏幕只指 16:9 / 16:10，即不为 21:9 单独投入。该问题作为已知取舍记录在规划文档，不在本轮实施。

## 4. 操作步骤

严格按序执行，每步完成后再进入下一步。

### 步骤 1 · 阈值与面板下界

1. `displayLayout.ts` 将 `MIN_HUD_SIDEBAR_WIDTH` 改为 `120`，注释写明「低于此宽度无法承载完整图文列，直接回退战场内 HUD」。
2. `HUDScene.ts` 将 `MICRO_SIDE_PANEL_MIN_WIDTH = 44` 改为 `COMPACT_SIDE_PANEL_MIN_WIDTH = 114`。
   - 原值 44 服务的是 `sidebarWidth = 50` 的微型档；阈值提到 120 后，`clamp` 下界实际永远是 `120 - 6 = 114`，保留 44 会成为不可达死值。
   - 保留 `clamp` 而不删除下界，是为了在 `DISPLAY_SIDEBAR_WIDTH` 出现异常值时仍有防御。

### 步骤 2 · 删除 `USE_MICRO_SIDE_HUD`

1. 删除第 99 行的变量声明与第 154 行的赋值。
2. 逐处塌缩三元分支，**保留非微型分支的取值**。共约 50 处，分两类：
   - `USE_MICRO_SIDE_HUD ? A : B` → 直接取 `B`。
   - `setVisible(!USE_MICRO_SIDE_HUD)` → 该对象在剩余全部侧栏形态都可见，改为 `setVisible(true)` 或直接删除该调用；`setVisible(USE_SIDE_HUD && !USE_MICRO_SIDE_HUD)` → `setVisible(USE_SIDE_HUD)`。
3. 特别留意三处非机械替换：
   - `ARSENAL_IMAGE_CENTER_X`（161 行）微型分支是 `Math.max(16, (SIDE_PANEL_WIDTH - 8) / 2)` 这类计算式，塌缩后应落到 `USE_NARROW_SIDE_HUD ? 25 : ...`。
   - `arsenalTitleText`（917 行）微型分支给的是不同文案，塌缩后统一用非微型文案。
   - `slot.ammo`（1431 行）空槽占位文字 `'空'` / `'待编入'`，塌缩后统一 `'待编入'`。

### 步骤 3 · 测试断言

1. 阈值边界：`49 / 50` 改为 `119 / 120`，即 `sidebarWidth = 119` 判 `fallback`、`= 120` 判 `compact`。
2. 原「1920×910 视口进入窄压缩侧栏」用例保留：该视口 `sidebarWidth` 恰为 120，正好是新阈值下界，是有价值的边界哨兵。
3. 补两条落点断言，锁死本轮的范围结论：16:10（如 1920×1200）判 `fallback`；21:9（2560×1080）判 `compact`。

### 步骤 4 · 规划文档同步

1. 新增「支持视口范围」一节，用第 2 章的落点表作为结论。
2. 删除 4.2.1 的微型形态行与正文中全部微型档规格；三种形态变两种。
3. `11.3` 表格删除微型档数值，`MIN_HUD_SIDEBAR_WIDTH` 改 120，面板下界改 114。
4. `11.6` 删除第 4、5 项（极端屏幕留白），改为记录本轮确立的范围结论与仍待决的窄形态存废。
5. `11.6` 第 2 项（微型档隐藏角色行与被动可感知性冲突）**随微型档取消而自然消解**，改为已解决并说明原因。
6. 第 9 章测试哨兵删除 1920×960（微型档），保留 1920×910 与 2560×1080。

## 5. 实施建议

1. 步骤 2 是本轮唯一的高密度机械改动，建议按行号从大到小改，避免前面的编辑导致后面行号漂移。
2. 每个三元分支塌缩后立即确认取的是「非微型」那一侧。判断依据是原表达式的分支顺序，不要凭字面猜测哪个值更合理。
3. `USE_NARROW_SIDE_HUD` **必须保留**：它的判据是面板宽度 `< 140`，覆盖 `sidebarWidth` 120–145，与被删除的微型档不是同一层。删错会导致窄形态直接套用宽形态排版而溢出。
4. 文档与代码同一轮改完，不留「文档说两种形态、代码还有三种」的中间态。

## 6. 潜在风险分析

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 三元分支塌缩取错分支 | 窄形态套用微型值，文字与图标显著过小 | 逐处核对分支顺序；重点复查 161、867、871 行这类多级嵌套 |
| 误删 `USE_NARROW_SIDE_HUD` | `sidebarWidth` 120–145 直接套宽形态，内容溢出侧栏压到战场 | 步骤 2 只删 `MICRO`，`NARROW` 全部保留 |
| 窄形态成为最窄形态后排版更紧张 | `sidebarWidth = 120` 时面板仅 114px，武器名可用宽度约 42px，长武器名（如「沙漠之鹰」）可能换行或截断 | 该形态改动前已存在、非本轮引入；记入待决项，留 V6 实景确认 |
| 已有测试断言失效 | `display-layout.test.ts` 的 49/50 断言必然失败 | 步骤 3 同轮更新 |
| `MICRO_SIDE_PANEL_MIN_WIDTH` 死值残留 | 后续读者误以为面板可以低到 44px | 步骤 1 改名改值 |
| 拖窗回退更早发生 | 用户从超宽窗口拖窄时，侧栏在 120px 就整体消失并重建为战场内 HUD，跨档比原先更早 | 属预期行为变化；跨档快照回灌逻辑不变，仍走既有 C 档路径 |

## 7. 优化方案

1. **只删形态不删能力**：微型档承载的信息在 C 档战场内 HUD 里全部有对应位置，因此取消它不会造成信息丢失，只是提前切换呈现方式。
2. **保留 `clamp` 防御**：面板宽度下界改值而非删除，避免异常 `sidebarWidth` 直接算出负宽度。
3. **测试锁死范围结论**：新增 16:10 与 21:9 两条落点断言后，将来若有人再调阈值，测试会直接暴露范围变化，而不是等到实景才发现。

按用户既有要求，本轮默认只做静态验证：

1. 全仓库检索确认 `USE_MICRO_SIDE_HUD` 与 `MICRO_SIDE_PANEL_MIN_WIDTH` 零残留。
2. 确认 `USE_NARROW_SIDE_HUD` 与 `USE_FULL_SIDE_HUD` 的全部分支完整保留。
3. 按 `resolveDisplayLayout()` 公式复算第 2 章落点表，确认改动后 16:9/16:10 仍判 `fallback`、21:9 仍判 `compact`。
4. 确认规划文档不再出现微型档规格，且阈值数字与代码一致。

**因为本轮修改了 `display-layout.test.ts` 的断言，静态验证无法证明测试通过。** 建议追加执行 `npm test`（vitest，预计数秒内完成）。是否执行需用户明确同意；未执行前不得声称测试已通过。

后续仍需的实景验证（V4 / V6，Agent 不能替代）：

1. 从 21:9 全屏拖窄到 16:9，确认在 `sidebarWidth = 120` 处一次性回退且不留残留对象。
2. `sidebarWidth = 120` 边界处窄形态的武器名是否截断。
3. 2560×1080 与 3440×1440 的实际可读性。

这一项超出第 3.1 节列出的范围，但属于同一改动的直接后果（不做就留下三个伪动态值），因此按第 7 章「只删形态不删能力」的原则一并完成，在此记录以保持可追溯。
