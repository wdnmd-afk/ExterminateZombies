## 3. 已确认事实与影响链路

README 以以下实现为事实来源：

1. `package.json`、`vite.config.ts`：技术栈、开发命令、构建输出和开发端口。
2. `src/main.ts`、`src/scenes/*`：场景流、菜单、关卡、图鉴、设置、结算和 HUD。
3. `src/config/*`：默认键位、关卡、武器、感染体、道具和图鉴条目。
4. `src/systems/*`：输入重绑定、波次、武器、道具、高清渲染和本地存档。
5. `src/assets/**/README.md`、`ATTRIBUTION.md`、`SOURCE.md`：第三方素材来源与许可。
6. `docs/TESTING.md`、`PROJECT_MASTER_PLAN.md`：验证入口、当前定位和后续规划。

## 4. 操作步骤

1. 检查 Git 状态，记录并保护已有未提交修改。
2. 阅读入口、配置、主要场景、系统和素材说明，建立当前功能清单。
3. 设计 README 结构，覆盖项目简介、当前内容、操作方式、快速开始、脚本、目录、配置入口、存档、测试、文档与许可。
4. 明确区分“当前已接入内容”和“仅在图鉴中展示但尚未开放的内容”。
5. 使用仓库相对路径链接代码和文档，避免依赖本机绝对路径。
6. 完成 README 后执行轻量验证，并将结果回填本执行文档。

## 5. 实施建议

1. 以当前代码行为为准，不复制未确认的历史计划结论。
2. README 保持面向玩家和开发者的双重可读性，避免堆叠内部实现细节。
3. 易变化的具体数值只做必要摘要，详细定义链接到对应配置文件。
4. 启动说明只使用 `package.json` 已存在的脚本，不新增依赖或命令。
5. 对项目源码许可与第三方素材许可分开说明，避免形成错误授权承诺。

## 6. 潜在风险分析

1. **文档漂移**：玩法和内容数量继续变化后，README 可能失真。通过链接权威配置并减少重复数值降低维护成本。
2. **功能过度承诺**：源码存在不等于已完成浏览器人工验收。README 将明确当前仍是开发中的可玩原型。
3. **许可误述**：素材包含 CC0、CC-BY 和 OGA-BY 等不同许可。README 只做概览，并指向完整来源与署名文件。
4. **覆盖用户改动**：工作区已有代码修改。实施过程只编辑两份 Markdown 文件，并在结束时复核 Git 状态。
5. **运行环境猜测**：项目未声明 Node.js `engines`。README 不写未经项目确认的精确 Node.js 版本。

## 7. 优化方案

1. 将可变的玩法数量集中在“当前内容”一节，后续版本更新时可快速复核。
2. 把详细测试流程保留在 `docs/TESTING.md`，README 只提供最短验证入口。
3. 将路线规划统一链接到 `PROJECT_MASTER_PLAN.md`，避免在 README 重复尚未锁定的方向。
4. 后续若加入正式发布流程，可再补充截图、在线试玩地址、浏览器兼容矩阵和版本徽章。

3. 检查 Markdown 围栏数量成对、表格与标题结构完整。
4. 执行 `git diff --check -- README.md docs/execution/2026-07-29-readme-refresh.md`。
