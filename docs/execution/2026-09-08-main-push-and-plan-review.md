## 3. 操作步骤

1. 核对工作区、提交身份、远端、忽略规则、活动钩子及新增资源大小，筛查待提交文本中的常见凭据形式。
2. 获取 `origin/main`，检查祖先关系；若出现分叉或权限问题，保留本地改动并明确说明，不使用强推绕过。
3. 审阅已冻结快照的摘要和空白差异，只更新本执行方案的暂存版本，以真实改动范围创建提交，不写成已验证通过。
4. 正常推送 `main`，读取远端分支提交号并与本地 HEAD 对照，单列仍在写入的新玩法改动，不清理或覆盖它们。
5. 在推送后阅读总规划、Goal 表、交接和相关执行文档，以当前源码、资源与既有验证证据核实未完成项。
6. 将未完成项区分为“实现仍缺失”“实现已有但缺验证”“台账/合规未收口”“重复或过期计划”，逐项给出继续、缩减、暂停或关闭的建议与原因。
7. 给出建议的下一批顺序及依赖条件；未经用户进一步确认，不据评估结果启动新实现或批量修改长期路线。

## 4. 实施建议

- 使用一个汇总提交保留当前连续工作批次的完整依赖关系，不拆散资源登记与消费端。
- 优先依据可执行代码和真实资产，再参考计划中的完成标签；不把多份文档中的同一待办重复计算。
- 区分玩家可见收益与工程维护收益，对只增加内容数量、装饰或抽象层的任务单独评估成本。
- 对仅缺真人体验判断的任务，不继续堆叠代码来代替验证；对许可与资源登记缺口，不用运行正常代替合规收口。

## 5. 潜在风险

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 未经命令验证的代码进入 main | 编译或运行问题尚未排除 | 保留未验证状态，推送不作为发布或上线动作 |
| 全量暂存包含本地敏感资料 | 凭据或调试数据进入远端 | 核对忽略规则、文件清单和常见凭据模式，不强制加入忽略项 |
| 并发开发污染提交边界 | 新玩法只提交了部分依赖 | 仅提交已审阅的暂存版本，保留后续工作区差异，新玩法另批收口 |
| 远端发生新提交 | 非快进推送或覆盖他人工作 | 推送前获取远端，禁止 force 与自动改写历史 |
| 旧文档与当前实现脱节 | 重复开发或无依据扩大范围 | 对照源码、资产和执行记录，分离实现完成与验收完成 |
| 计划复核被误解为授权实施 | 擅自增加新工作或测试 | 本轮只给建议，不启动后续功能开发或验证命令 |

## 6. 优化方案

用“实际缺口、当前玩家价值、依赖条件、实施/维护成本”评估任务，而不是只按旧编号顺序续做；合并重复验收入口，将发布前硬门槛与可延后优化分开，避免把缺证据的项目误判成缺更多功能。

## 7. 验证方式

- 允许的静态核对：Git 状态、差异/空白检查、文本凭据筛查、提交对象与远端 HEAD 对照、代码和文档阅读。
- 本轮明确不执行：`npm test`、`npm run typecheck`、任何 lint/build、浏览器或服务启动。
- 推送证据：本地提交号、远端 `refs/heads/main` 提交号、推送结果以及最终工作区状态。
- 计划评估证据：对应 Goal/执行文档路径及关键源码引用；无法由静态阅读证明的体验、性能与视觉质量明确保留为待验证。
