## 1. 目标

把宽屏视口左右两侧的黑边变成一等 HUD 空间，让关卡内信息以「常驻仪表盘」的形式呈现在战场之外，战场画面上只保留必须抢注意力的瞬时浮层。

本规划要达成：

1. 左右侧栏成为常驻信息区，分工固定：左＝玩家自身状态，右＝关卡情报。
2. 武器栏从「1.8 秒后淡出的弹出层」改为侧栏常驻模块，并按 5 个出战槽预留充裕空间。
3. 新增当前不存在的关卡情报：关卡总进度条。
4. 侧栏宽度不足时有明确的三档降级，不出现挤压、截断或溢出。
5. 窗口尺寸变化与进出全屏时重新计算侧栏，中央战场始终保持 `1280×720`，且重排不丢失战局与 HUD 瞬时状态。
6. 只覆盖正常屏幕与主流超宽屏，不为极端屏幕做专门处理，范围结论见 2.1。

明确不在本规划范围（需要时另开文档）：

1. 武器拖拽排序、预设编队和局内替换已满编队；本轮只提供点击编入/移出与稳定槽位顺序。
2. 局内复盘数据：命中率、爆头数、承伤、生存时长。
3. 敌情档案卡、下一波预告与倒计时、段落进度与同屏上限。
4. 战术日志流、垂直关卡时间轴等替代呈现形式。
5. 主菜单、图鉴、结算等非战斗场景的宽屏适配。
6. 角色区块升级为头像或立绘形态、以及在侧栏展开角色四项属性详情；本轮只保留左侧栏首行的 `代号 · 被动状态`，理由见 3.5。

### 2.1 支持视口范围

> **更正（2026-08-19）**：本节下表按**显示器分辨率**代入 `resolveDisplayLayout()`，但 `DisplayManager.ts:12-15` 实际喂入的是 `window.innerWidth / window.innerHeight`（浏览器视口）。浏览器 chrome 占掉高度后视口一定比 16:9 更宽，因此**下表与结论 1 只在真全屏下成立**。窗口化时 1080p 显示器的实际视口约 1920×919（宽高比 2.089），算出 `sidebarWidth = 113`，落在 B 压缩档门槛 120 之下 1 步之遥——这正是「一直看到两条纯色边」的根因：空间算出来了却被阈值丢掉。修正方案与实算落点见 `docs/playDesign/药品与固定侧栏HUD.md` 第 6 节。

用户 2026-08-18 明确要求：**不兼容极端屏幕，只兼容正常屏幕**，并确认「正常屏幕」只指 16:9 / 16:10。本节据此把各类屏幕的实际落点写成结论，按 `resolveDisplayLayout()` 公式演算，不是估算：

| 屏幕（**真全屏**） | 宽高比 | `sidebarWidth` | 档位 | 支持级别 |
| --- | ---: | ---: | --- | --- |
| 1920×1080 / 2560×1440 / 3840×2160 | 1.78 | 0 | C 回退 | 保证 |
| 1920×1200 / 2560×1600 | 1.60 | 0 | C 回退 | 保证 |
| 2560×1080 | 2.37 | 214 | B 宽压缩 | 保证 |
| 3440×1440 | 2.39 | 220 | B 宽压缩 | 保证 |
| 3840×1600 | 2.40 | 224 | B 宽压缩 | 保证 |
| 5120×1440 / 3840×1080 | 3.56 | 640 | A 全量 | 可用，不专门优化 |

补充：窗口化（非全屏）时的实际落点，按视口尺寸演算：

| 视口 | 宽高比 | `sidebarWidth` | 档位 |
| --- | ---: | ---: | --- |
| 1920×919（1080p 显示器 + 浏览器 chrome） | 2.09 | 113 | C 回退（差 7px 进 B 档） |
| 1366×700 | 1.95 | 63 | C 回退 |
| 2560×1279（1440p 显示器 + chrome） | 2.00 | 81 | C 回退 |

三条必须记住的结论：

1. **本节是固定侧栏实施前的历史落点。** 该取舍已由 `药品与固定侧栏HUD.md` 推翻并完成代码实施：`sidebarWidth` 现在至少为 120，正常屏幕进入 B 压缩档，C 档代码保留但运行时不可达；命令与实景验证仍待完成。
2. **A 档门槛是宽高比 ≥ 2.500**，恰好落在 21:9（2.37–2.40）与 32:9（3.56）之间的空隙，市面上没有该比例的显示器。现实中只有 32:9 能进入 A 档。
3. **21:9 拿不到全量档**是已知取舍：用户已表态正常屏幕只指 16:9 / 16:10，即不为 21:9 单独投入。本规划记录该事实，不做阈值调整。

超宽屏留白（32:9 下面板 220px、两侧各留约 420px）按「不兼容极端屏幕」处理，不再列为待决项。

## 3. 现状事实

### 3.1 侧栏地基已经存在

`resolveDisplayLayout()` 按视口宽高比算出 `sidebarWidth`，常量 `MIN_HUD_SIDEBAR_WIDTH = 120` 决定 `hasHudSidebars`。`HUDScene` 按运行时档位切换战场内与侧栏排布，`configureHighResolutionScene(this, { includeSidebars: true })` 让 HUD 摄像机拿到完整宽画布。

所以本规划是在既有地基上扩容与规范化，不是从零搭建。

### 3.2 固定战场与动态侧栏边界

`src/main.ts:16-26` 使用固定 `width` / `height` 加 `Phaser.Scale.FIT`，由此：

1. 画布逻辑宽高比在**模块加载时一次性锁死**。
2. 改变窗口不会让侧栏内容错位——整块画布等比缩放，元素相对位置保持不变。
3. 真正的缺陷是宽高比不再变化：16:9 开局后切到带鱼屏永远拿不到侧栏；21:9 开局后缩小窗口则是战场被白白压小。

用户 2026-08-18 明确要求中央游戏画面保持固定、侧栏只使用剩余空间，并进一步确认侧栏整体规划需要完整执行。因此运行中使用 `game.scale.setGameSize()` 更新渲染画布宽度，所有战斗摄像机仍只观察中央 `1280×720`；HUD 摄像机观察完整画布并在 A/B/C 跨档时重建布局。

### 3.3 关卡进度条几乎不需要新数据

改为关卡级进度条之后，所需数据已经全部就位：`state.waveIndex` 与 `GameScene.getWaveTotal()`（`src/scenes/GameScene.ts:366`）当前已经在喂 `WAVE 3/8` 这行文本。进度条只是把同一对数字换成条形呈现。

这是砍掉本波进度条换来的直接收益：原本需要给 `WaveManager` 新增波次级快照、缓存本波敌人总量、并额外暴露场上存活计数，这三项现在全部不必做。`getProgressSnapshot()`（`src/systems/WaveManager.ts:183`）保持原样继续服务性能压测。

唯一需要补的是 BOSS 刻度标记，见 5.2。

### 3.4 武器栏本来就是动态槽位

`getWeaponStatuses()`（`src/systems/WeaponManager.ts:431`）按 `ownedWeapons` 逐项返回；改造前 HUD 的 8 个槽只是对象池，多余槽会 `setVisible(false)`。所以「改成 5 槽」不是截断当前状态，而是先由编队规则把本局武器限制在 5 把，再按真实编队逐项渲染。

两处约束已在实现中收口：

1. `ownedWeapons` 仍可通过 `pickupWeapon()` 增长，但总数受 5 把上限约束；满编队的新武器只解锁许可。
2. `keybinds` 已增加 `weapon5`，默认数字键为 `5`，并同步进入设置页和存档迁移。

### 3.5 左侧栏顶部已经在显示角色状态

角色与战前整备系统落地后，`HUDScene` 在左侧栏最顶部新增了一行角色状态（`src/scenes/HUDScene.ts:609`），本规划前几版没有记录它，本版补齐：

1. 内容是 `代号 · 被动状态`，由 `getCharacterDef(state.player.characterId)` 取配置后拼接。
2. 被动状态按角色分支：守望者显示 `余生就绪` / `余生已用`，鹰眼显示 `校准中` / `校准完成`，其余三名角色直接显示被动名称。
3. 文字颜色运行时改为该角色的 `accentColor`，创建时的 `#58c9dd` 只是占位色。
4. 该行位于生命之上，是左侧栏第一行，因此**左侧栏的信息顺序是「角色 → 生命 → 武器与弹药 → 武器栏 → 道具」**，4.1 的分区图据此更新。
5. 取消微型形态后，该行在**全部侧栏档位都常驻**，不再有「某一档看不到被动状态」的情况。

这一行属于既有实现，不是本规划新增需求。规划侧的决策只有一条：**保持单行文字形态，不升级为带头像的独立区块**。理由是升级成头像区块会连带引入角色档案立绘的裁切规格、区块高度、空状态处理和一档档的缩放规则，属于扩容而不是补记；而单行已经同时承载了代号与被动状态两项关键信息，本身扫视成本就很低。

### 3.6 内容面板宽度与侧栏宽度是两个量

这是前几版遗漏、但影响所有排版判断的事实。侧栏宽度 `sidebarWidth` 只决定「有多少黑边可用」，真正约束排版的是内容面板宽度 `SIDE_PANEL_WIDTH`，由 `resolveSidePanelWidth()`（`src/scenes/HUDScene.ts:145`）换算：

```text
A 档（full）    ：面板恒为 SIDE_PANEL_MAX_WIDTH = 220px，侧栏更宽时多出的空间留白，面板不再变宽
B 档（compact） ：面板 = clamp(sidebarWidth - 6, 114, 156)
C 档（fallback）：面板 = 0，走战场内 HUD
```

三个推论必须写进规划，否则 11.3 的宽度估算无从校验：

1. **A 档面板不随侧栏增长。** 32:9 超宽屏不会得到更宽的面板，只会得到更宽的留白。所以 A 档排版只需要按 220px 一个宽度设计，不存在「A 档也要弹性」的问题。
2. **B 档面板在 `sidebarWidth = 162px` 时就已封顶 156px。** 162–259px 区间内面板宽度完全不变，只是留白变宽。因此 B 档的排版上界是 156px，不是 259px。
3. **`clamp` 下界 114px 正常不可达。** 侧栏最小 120px 减 6px 即 114px，因此下界只是异常侧栏宽度的防御值，不代表任何真实形态。


## 4. 布局规格

三档以 `sidebarWidth` 为唯一判据。阈值集中在 `displayLayout.ts`，`HUDScene` 只消费结果，不自己判断宽度。

规则：

1. **角色行常驻在左侧栏首行**，内容 `代号 · 被动状态`，12px，取角色 `accentColor`。它是玩家状态区的标题行，不单独成块、不加头像，理由见 3.5。
2. 5 个出战槽全部常驻。切枪只改高亮与描边，不再整块淡入淡出。

4. 每槽行高从当前 40px 放宽到 ~56px，武器图标随之放大。武器美术仍在迭代，槽内要留得下更大的枪械图，这是「预留更多空间」的主要落点。
5. 第 1 槽固定是手枪且不可更换，视觉上与其余 4 槽区分（例如序号位加锁标或换底色），让「这一格换不了」不需要读说明就能看出来。
6. BOSS 区块无 BOSS 时整块隐藏，下方区块**不上移**——槽位固定是仪表盘的前提，跳动比留白更难读。
7. 关卡进度条按 `waveIndex / getWaveTotal()` 填充，波次刻度画在条下方；关卡含 BOSS 时在末端标 ☠。无尽模式没有总数，退化为纯计数文本，不画条形。
8. 右侧栏顶部按「模式 → 关卡名 → 波次」三行排列，模式用警戒黄、关卡名用弱化灰、波次用 20px 旧纸白，形成一条从属性到主数值的字号阶梯。


### 4.2 B 档 · 压缩（`120 ≤ sidebarWidth < 260`）

在 A 档基础上按固定顺序削减，直到内容装得下：

| 顺序 | 削减动作 |
| --- | --- |
| 1 | 强化列表从「最近两张卡名」压成「强化 2」一行计数 |
| 2 | 弹药详情行（`备用 120 · 连发`）整行隐藏，只保留弹药数与弹药条 |
| 3 | 关卡进度条去掉波次刻度与刻度文字，只留条形与 `WAVE 3/8`，条高从 9px 收到 7px |
| 4 | 武器槽行高从 56px 收到 44px，武器图标缩小但保留 |
| 5 | 关卡名整行隐藏，右侧栏顶部只留模式标签 |

第 2 项与第 5 项是**隐藏而非合并**：`ammoDetailText` 与 `levelText` 在整个 B 档都不可见。前几版写成「合并进上一行」，与实现不符，本版按代码更正——合并需要重新拼接文案，而实现选择的是整行让位，两者的验收标准不同。

#### 4.2.1 压缩档内部的两种形态

档位主结构是三档，与 `displayLayout.ts` 的 `HudSidebarTier` 一一对应；B 档内部再按面板宽度分两种形态，由 `HUDScene` 自己判定，不进枚举：

| 形态 | 判据 | `sidebarWidth` | 内容面板 | 槽行高 | 武器图标 |
| --- | --- | --- | ---: | ---: | ---: |
| 宽压缩 | 默认 | 146–259 | 140–156px | 44px | 40×24 |
| 窄压缩 | `SIDE_PANEL_WIDTH < 140` | 120–145 | 114–139px | 44px | 32×20 |

判据是**面板宽度而不是侧栏宽度**。因为面板 = `sidebarWidth - 6`，`SIDE_PANEL_WIDTH < 140` 等价于 `sidebarWidth < 146`。

窄压缩形态不隐藏任何文字，只调字号与纵向间距：角色行 12px → 10px，武器名与弹药数 22px → 18px，武器图标 40×24 → 32×20，道具图标左移 6px。左右面板高度在两种形态下相同（155px / 128px）。

**原「微型」形态（`sidebarWidth` 50–119）已在 2026-08-18 取消**，判据变量 `USE_MICRO_SIDE_HUD` 及其全部分支已从代码中删除。取消原因是它对应的宽高比 1.92–2.11 没有任何标准显示器落在其中，只在窗口化拖拽的中间过程被短暂经过；与其维护一个只剩图标的残缺形态，不如让 `MIN_HUD_SIDEBAR_WIDTH` 直接把这段宽度归入 C 档。信息没有丢失——微型档承载的内容在 C 档战场内 HUD 里全部有对应位置。详见 `docs/execution/2026-08-18-hud-viewport-scope.md`。

武器槽的图标是**最后才动**的一项，且只缩小不删除。整个改造的出发点就是给武器留更多空间，压缩档不应该先把它牺牲掉。

削减是**声明式的**：每个模块声明自身在压缩档的形态，不写「如果宽度小于 X 就 setVisible(false)」这类散落分支。


### 4.3 C 档 · 回退（`sidebarWidth < 120`）

维持现有战场内 HUD，即当前 `USE_SIDE_HUD === false` 的全部排布，不做改动。武器栏在这一档仍保持「切枪弹出、1.8 秒淡出」的旧行为——战场内没有常驻空间。

这意味着武器栏要同时保留两种生命周期。取消自动隐藏只发生在 A / B 两档。

按 2.1，**全部正常屏幕（16:9 / 16:10）都落在这一档**。因此 C 档不是边缘情况，而是绝大多数玩家实际看到的形态。本轮不重做它，但后续若要投入 HUD 视觉，优先级应高于继续打磨侧栏。

### 4.4 侧栏视觉口径与战前整备的一致性

侧栏和战前整备页是玩家连续经过的两个界面（整备 → 开战），配色不同源会让人感到换了一套 UI。本节先把两边的现状记成事实，再指出唯一的不一致点。

侧栏当前实际用色：

| 区块 | 底色 | 描边/强调 | 代码位置 |
| --- | --- | --- | --- |
| 左侧栏（玩家状态） | `0x11151c` / 0.62 | `0x58c9dd` 青 / 0.22 | `HUDScene.createLeftPanel` 段 |
| 军械面板 | `0x11151c` / 0.68 | `0x58c9dd` 青 / 0.2 | `HUDScene.createArsenal()` |
| 道具面板 | `0x11151c` / 0.62 | `0x58c9dd` 青 / 0.18 | `this.itemPanel` |
| 右侧栏（关卡情报） | `0x17140f` / 0.62 | `0xfbc02d` 警戒黄 / 0.22 | `this.rightPanel` |
| 侧栏内缘竖线 | — | 左 `0x58c9dd` / 右 `0xfbc02d`，均 0.48 | `leftSidebarEdge` / `rightSidebarEdge` |
| C 档战场内面板 | `0x101116` / 0.82 | `0xf4eedd` 旧纸白 / 0.42 | 同上对象的非侧栏分支 |

即侧栏是**左冷右暖**：左侧栏偏冷蓝黑配青色，右侧栏偏暖褐黑配警戒黄。这是有意的语义分色——冷色是「我方状态」，暖色是「战场情报」，扫视时不必读字就能分辨看的是哪一侧。本版把它确认为已锁定决策，不再当作待定项。

与战前整备页（`PreparationScene.ts`）对照：

| 角色 | 整备页 | 侧栏 | 是否同源 |
| --- | --- | --- | --- |
| 页面底色 | `0x101014` | `0x11151c` / `0x17140f` | 同族深黑，可接受 |
| 主文字 | `0xf4eedd` 旧纸白 | `0xf4eedd` 旧纸白 | 一致 |
| 操作/强调 | `0xfbc02d` 警戒黄 | 右侧栏描边、模式标签、道具详情同为 `0xfbc02d` | 一致 |
| 风险/危险 | `0xd32f2f` 血红 | 生命条 `0xd9574e`、低血红光 | 同族，不同值 |
| 弱化信息 | `0xf4eedd` 低透明度 | `#aab2b8` 灰 | 不同实现，观感接近 |
| 青色 | **没有** | 左侧栏与道具面板描边 `0x58c9dd` | **不同源** |

结论：右侧栏的暖色系已经和整备页共用同一套口径，旧纸白与警戒黄全局一致；**唯一的外来色是左侧栏的青色 `0x58c9dd`**，整备页没有任何位置使用它。

这一点不在本轮改动范围内，因为它是取舍而非缺陷：青色换来了左右分色的可读性，代价是与整备页少一层呼应。是否把左侧栏改成整备页也有的色（例如降低饱和度的旧纸白描边），需要美术口径，列入 11.6。

另外两处与角色系统相关的用色已确认，不需要额外决策：

1. 角色行文字色在运行时被 `accentColor` 覆盖，因此左侧栏首行的颜色由角色决定，不属于侧栏配色体系；整备页角色卡也使用同一 `accentColor`，两边天然一致。
2. 道具详情用警戒黄 `#fbc02d`，与整备页的操作焦点色一致。

## 5. 数据接口需求

### 5.1 出战编队

编队已经纳入本轮实现，统一由 `SaveManager.getWeaponLoadout()` 提供：

```ts
/** 已保存出战武器，按槽位顺序；第 0 项固定是手枪，最多 5 把。 */
getWeaponLoadout(): WeaponId[]
```

已锁定行为：

1. 武器库只允许已解锁许可的武器编入，手枪不可移除。
2. 新存档首次进入战前整备时从全部 8 把武器中选满 5 把，手枪固定占第 1 槽；所选武器同时获得许可，未选武器仍可通过战场拾取解锁。
3. 本局 `ownedWeapons` 不超过 5；局内有空位时新武器可加入当前战局，满员时不创建临时第 6 槽。
4. 新增 `weapon5`，默认数字键为 `5`，设置页可以改绑。
5. 第一关仍以手枪作为当前武器，但保留已经选择的其它编队武器。

### 5.2 关卡进度条

数据已经就位，不新增系统接口：

```text
进度 = waveIndex / getWaveTotal()
```

`state.waveIndex` 与 `GameScene.getWaveTotal()`（`src/scenes/GameScene.ts:366`）就是现在 `WAVE 3/8` 文本的数据源。需要补的只有两点：

1. **BOSS 刻度**：`GameScene.hasBossWave()` 已提供只读判断，进度条末端按该结果显示 Boss 标记。
2. **无尽模式**：`getWaveTotal()` 返回 `null`，没有分母。此时不画条形，退化为纯计数文本 `WAVE 17`。

### 5.3 刷新时机

进度条只在波次推进时变化，跟随现有的 `EVENTS.waveChanged` 刷新即可，不需要新事件，也不需要每帧更新。


## 6. 动态显示适配方案

### 6.1 本轮职责

| 层 | 职责 | 触发 |
| --- | --- | --- |
| `resolveDisplayLayout()` | 根据实时视口计算逻辑宽度、等宽侧栏和 A/B/C 档 | 页面加载、窗口变化、全屏变化 |
| `Phaser.Game.scale` | 去抖后 `setGameSize()` 更新渲染画布，继续由 `FIT` 适配父容器 | 布局结果变化 |
| 场景摄像机 | 战斗场景只看中央 1280×720，HUD 场景看完整宽画布 | 场景创建、布局变化 |
| HUD 布局 | 同档位更新根容器位置；跨档位重建并回灌快照 | 布局变化 |

### 6.2 运行中窗口变化

窗口或全屏变化去抖约 150ms 后重新计算侧栏。只有逻辑宽度实际变化时才调用 `setGameSize()`；中央战场物理与世界边界不变，非 HUD 场景摄像机重新居中，输入继续通过更新后的 GameScene 摄像机换算。

### 6.3 HUD 状态保全

跨档时保存战斗警报及剩余时长、连杀显示、里程碑、拾取提示、C 档军械带剩余显示时间和暂停原因；重建后只恢复仍有剩余时间的瞬时内容。休眠中的 HUD 只标记布局过期，唤醒时再重建，避免窗口变化意外唤醒挂起战局。

## 7. 中央浮层处理

四个浮层保留在战场上，不迁入侧栏：

| 浮层 | 位置 | 说明 |
| --- | --- | --- |
| 波次公告 | 战场中央偏上 | 保持现有 y ≈ 126 |
| 战斗警报 | 战场中央偏上，公告下方 | 需要改为**居中**，见下 |
| 连杀里程碑 | 战场中央 | 保持现有 y ≈ 300 |
| 拾取提示 | 战场下方居中 | 保持现状 |

需要修正的一处：战斗警报当前是**左对齐 + 右对齐分列**（`COMBAT_ALERT_LEFT + 22` 起标题、右缘 `-22` 贴副标题，`src/scenes/HUDScene.ts:495-504`），而且横向锚点是为「避开战场内左侧状态板」算出来的。侧栏化之后战场左上不再有面板，这个偏移失去理由。

浮层始终锚定战场坐标（1280×720 中央），不随侧栏宽度变化而位移。

## 10. 风险与未决

1. **编队会改变既有弹药经济样本。** 五把开局武器各有满弹匣，但仍只给当前主武器一个备用弹匣；需要通过后续完整试玩确认补给压力没有被明显稀释。
2. **满编队拾取新武器不再立即装备。** 该拾取仍解锁许可并给出武器库提示；新存档第一关有空位，固定 MP5 教学不受影响。
3. **B 档排版仍可能过密。** 120–145px 使用窄图文列（只降字号、不隐藏文字），146px 以上使用宽图文列，内容面板在 `sidebarWidth = 162px` 时封顶 156px，之后只增加留白。两段区间与判据见 4.2.1。窄形态下面板仅 114–139px，武器名可用宽度约 42–67px，长武器名是否截断需 V6 实景确认。
4. **运行中跨档会重建 HUD。** 已通过快照回灌警报、拾取、连杀、军械显示和暂停状态，但仍需实景验证抽卡层级、休眠战局唤醒和连续跨档不会留下监听器。取消微型档后回退发生得更早（120px 而非 50px），跨档路径不变但触发点前移。
5. **动态宽度使用会话内固定渲染倍率。** 本轮只改变逻辑画布宽度，不在运行中切换 `DISPLAY_RENDER_SCALE`，避免文字纹理与全部摄像机同时换倍率。
6. **关卡进度条在无尽模式下没有意义。** 无尽模式没有总波数，退化为纯计数。这等于无尽模式拿不到本规划新增的唯一情报项，右侧栏会比闯关模式空一块。是否给无尽模式换一个替代指标（例如最佳波次对比）留待后续，本规划不做。
7. **主观可读性未验。** 侧栏字号在真实显示设备上是否够读、放大后的武器图标是否清晰、仪表盘信息密度是否过高，属于 V6 真人验收，Agent 不能替代结论。
8. **侧栏 HUD 服务的用户比例可能很小。** 按 2.1，正常屏幕全部走 C 档，侧栏只对 21:9 及更宽生效。这不是缺陷，但意味着后续 HUD 投入的优先级判断应以 C 档为主。

### 11.6 待补充

本节记录尚未定稿的空白，即前面章节已写清事实、但结论仍需美术或试玩口径的项。每项都注明它会回填到哪一节。

1. **左侧栏青色 `0x58c9dd` 的去留。** 事实已记在 4.4：它是战前整备页完全没有的色。保留则维持左冷右暖的分色可读性，改掉则整套 UI 只用旧纸白/警戒黄/血红三色。需要美术口径，结论回填 4.4 与 11.2 第 6 项。

2. **字号阶梯是否收敛。** 11.2 第 2 项已列出全部在用字号（10/12/13/16/18/20/22px）与各档的降级关系。是否压成统一 3–4 级 scale 属于视觉决策，需要美术口径后回填 11.2 第 2 项。

3. **窄压缩形态的武器名是否截断。** 窄形态面板 114–139px，武器名可用宽度约 42–67px。`fitTextWidth` 会压缩超宽文本，但「沙漠之鹰」这类四字武器名在 42px 下的实际观感需要 V6 确认，结论回填 4.2.1。这也是取消微型档后仍存在的最窄真实形态。

4. **C 档是否单独立项。** 见 11.4 第 1 项。这是本轮范围收缩后最需要判断的方向性问题：正常屏幕全部走 C 档，而 C 档在本规划里始终是「维持现状」。
