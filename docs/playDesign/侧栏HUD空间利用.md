# 侧栏 HUD 空间利用规划

> 文档状态：规划稿 v0.1
> 建立日期：2026-08-18
> 所属层级：`docs/playDesign/` — 单项玩法与界面规划
> 事实来源：`src/ui/displayLayout.ts`、`src/systems/DisplayManager.ts`、`src/scenes/HUDScene.ts`、`src/main.ts`、`src/systems/WaveManager.ts`
> 关联：`PROJECT_MASTER_PLAN.md`、`TESTING_RULES.md`

## 1. 目标

把宽屏视口左右两侧的黑边变成一等 HUD 空间，让关卡内信息以「常驻仪表盘」的形式呈现在战场之外，战场画面上只保留必须抢注意力的瞬时浮层。

本规划要达成：

1. 左右侧栏成为常驻信息区，分工固定：左＝玩家自身状态，右＝关卡情报。
2. 武器栏从「1.8 秒后淡出的弹出层」改为侧栏常驻模块，并按 5 个出战槽预留充裕空间。
3. 新增当前不存在的关卡情报：关卡总进度条。
4. 侧栏宽度不足时有明确的三档降级，不出现挤压、截断或溢出。
5. 窗口尺寸变化与进出全屏时侧栏跟随重排，且不打断正在播放的动画与警报。

明确不在本规划范围（需要时另开文档）：

1. **出战编队本身**：在武器库里挑选 5 把出战武器、手枪固定不可更换的选择流程与存档。本规划只消费它的结果，依赖关系见 5.1。
2. 局内复盘数据：命中率、爆头数、承伤、生存时长。
3. 敌情档案卡、下一波预告与倒计时、段落进度与同屏上限。
4. 战术日志流、垂直关卡时间轴等替代呈现形式。
5. 主菜单、图鉴、结算等非战斗场景的宽屏适配。


## 2. 已锁定决策

| 项 | 决策 |
| --- | --- |
| 呈现格式 | 仪表盘：分区固定、槽位常驻、扫一眼可读 |
| 左侧栏 | 玩家状态——生命、当前武器与弹药、武器栏、道具 |
| 右侧栏 | 关卡情报——关卡与模式、关卡总进度条、BOSS、分数与强化 |
| 武器栏 | 改为常驻，取消自动隐藏；按 5 个出战槽预留充裕空间 |
| 新增情报 | 只做关卡总进度条一项；不做本波进度条 |
| 无黑边时 | 保持双套布局，16:9 继续回退到战场内 HUD |
| 响应式重排 | 纳入本规划；侧栏包成 Container，resize 只移容器 |
| 降级阶梯 | 三档：全量 / 压缩 / 回退 |
| 中央浮层 | 波次公告、战斗警报、连杀里程碑、拾取提示保留在战场中央偏上，内容居中 |

## 3. 现状事实

### 3.1 侧栏地基已经存在

`resolveDisplayLayout()`（`src/ui/displayLayout.ts:16`）按视口宽高比算出 `sidebarWidth`，常量 `MIN_HUD_SIDEBAR_WIDTH = 180` 决定 `hasHudSidebars`。`HUDScene` 以模块级 `USE_SIDE_HUD` 为开关，`LEFT_PANEL_*` / `RIGHT_PANEL_*` 两套常量已经分别覆盖「战场内」与「侧栏」两种排布，`configureHighResolutionScene(this, { includeSidebars: true })` 也已经让 HUD 摄像机拿到完整宽画布。

所以本规划是在既有地基上扩容与规范化，不是从零搭建。

### 3.2 必须修正的技术前提

`src/main.ts:16-26` 使用固定 `width` / `height` 加 `Phaser.Scale.FIT`，由此：

1. 画布逻辑宽高比在**模块加载时一次性锁死**。
2. 改变窗口不会让侧栏内容错位——整块画布等比缩放，元素相对位置保持不变。
3. 真正的缺陷是宽高比不再变化：16:9 开局后切到带鱼屏永远拿不到侧栏；21:9 开局后缩小窗口则是战场被白白压小。

因此第 6 章的响应式方案必须包含 `game.scale.resize()`，只移动容器不足以解决问题。

### 3.3 关卡进度条几乎不需要新数据

改为关卡级进度条之后，所需数据已经全部就位：`state.waveIndex` 与 `GameScene.getWaveTotal()`（`src/scenes/GameScene.ts:366`）当前已经在喂 `WAVE 3/8` 这行文本。进度条只是把同一对数字换成条形呈现。

这是砍掉本波进度条换来的直接收益：原本需要给 `WaveManager` 新增波次级快照、缓存本波敌人总量、并额外暴露场上存活计数，这三项现在全部不必做。`getProgressSnapshot()`（`src/systems/WaveManager.ts:183`）保持原样继续服务性能压测。

唯一需要补的是 BOSS 刻度标记，见 5.2。

### 3.4 武器栏本来就是动态槽位

`getWeaponStatuses()`（`src/systems/WeaponManager.ts:431`）按 `ownedWeapons` 逐项返回，HUD 里的 8 个槽只是对象池，多余的槽 `setVisible(false)`。所以「改成 5 槽」不是砍功能，而是把池上限和布局按出战编队的实际规模重算，并把腾出来的纵向空间还给每一槽。

两处需要留意：

1. `ownedWeapons` 目前会在局内通过 `pickupWeapon()`（`src/systems/WeaponManager.ts:382`）增长，起始只有 2 把。出战编队落地后这个增长模型要一并确认，属于 5.1 的依赖。
2. `keybinds` 只定义了 `weapon1`–`weapon4`（`src/config/keybinds.ts:24`），数字键覆盖不到第 5 槽。5 槽编队需要补一个 `weapon5`，否则第 5 把枪只能靠滚轮切到。


## 4. 布局规格

三档以 `sidebarWidth` 为唯一判据。阈值集中在 `displayLayout.ts`，`HUDScene` 只消费结果，不自己判断宽度。

### 4.1 A 档 · 全量（`sidebarWidth ≥ 260`）

```text
左侧栏                      右侧栏
┌──────────────────┐        ┌──────────────────┐
│ 生命      86/100 │        │ 关卡 2-3    生存 │
│ ████████████░░░░ │        ├──────────────────┤
├──────────────────┤        │ 关卡进度 WAVE 3/8│
│ M4A1             │        │ ██████░░░░░░░☠   │
│ 24/30            │        │ │  │  │       │  │
│ 备用 120 · 连发  │        │ W1 W2 W3     W8  │
│ ████████████░░░░ │        ├──────────────────┤
├──────────────────┤        │ BOSS  //  坦克   │
│ 出战武器         │        │ P2/3  破绽 2.4s  │
│ ┌──────────────┐ │        │ ███████████░░░░  │
│ │ 1 锁   [枪图] │ │        ├──────────────────┤
│ │ 沙漠之鹰 7/48 │ │        │ 1280 分          │
│ └──────────────┘ │        │ 强化 2/2         │
│ ┌──────────────┐ │        │ ▸ 连射改造       │
│ │ 2      [枪图] │ │        │ ▸ 加长弹匣       │
│ │ MP5    30/180 │ │        └──────────────────┘
│ └──────────────┘ │
│ ┌──────────────┐ │
│ │ 3      [枪图] │ │
│ │ M4A1   24/120 │ │
│ └──────────────┘ │
│ …（共 5 槽常驻） │
├──────────────────┤
│ ◈ 地雷      ×3   │
└──────────────────┘
```

规则：

1. 5 个出战槽全部常驻。切枪只改高亮与描边，不再整块淡入淡出。
2. 槽位数量由出战编队规模决定，不硬编码。编队未落地前按 `ownedWeapons.length` 渲染，上限 5。
3. 每槽行高从当前 40px 放宽到 ~56px，武器图标随之放大。武器美术仍在迭代，槽内要留得下更大的枪械图，这是「预留更多空间」的主要落点。
4. 第 1 槽固定是手枪且不可更换，视觉上与其余 4 槽区分（例如序号位加锁标或换底色），让「这一格换不了」不需要读说明就能看出来。
5. BOSS 区块无 BOSS 时整块隐藏，下方区块**不上移**——槽位固定是仪表盘的前提，跳动比留白更难读。
6. 关卡进度条按 `waveIndex / getWaveTotal()` 填充，波次刻度画在条下方；关卡含 BOSS 时在末端标 ☠。无尽模式没有总数，退化为纯计数文本，不画条形。


### 4.2 B 档 · 压缩（`180 ≤ sidebarWidth < 260`）

在 A 档基础上按固定顺序削减，直到内容装得下：

| 顺序 | 削减动作 |
| --- | --- |
| 1 | 强化列表从「卡名逐行」压成「强化 2/2」一行计数 |
| 2 | 弹药详情行（`备用 120 · 连发`）合并进弹药数行 |
| 3 | 关卡进度条去掉波次刻度，只留条形与 `WAVE 3/8` 文本 |
| 4 | 武器槽行高从 ~56px 收到 ~44px，武器图标缩小但保留 |
| 5 | 关卡标签与模式标签合并为一行 |

武器槽的图标是**最后才动**的一项，且只缩小不删除。整个改造的出发点就是给武器留更多空间，压缩档不应该先把它牺牲掉。

削减是**声明式的**：每个模块声明自身在压缩档的形态，不写「如果宽度小于 X 就 setVisible(false)」这类散落分支。


### 4.3 C 档 · 回退（`sidebarWidth < 180`）

维持现有战场内 HUD，即当前 `USE_SIDE_HUD === false` 的全部排布，不做改动。武器栏在这一档仍保持「切枪弹出、1.8 秒淡出」的旧行为——战场内没有常驻空间。

这意味着武器栏要同时保留两种生命周期。取消自动隐藏只发生在 A / B 两档。

## 5. 数据接口需求

### 5.1 出战编队（外部依赖，本规划不实现）

武器栏槽位数由出战编队决定。编队功能本身另开文档，但本规划依赖它最终提供：

```ts
/** 本局出战武器，按槽位顺序；第 0 项固定是手枪。 */
getLoadout(): readonly WeaponId[]
```

在编队落地之前，HUD 按现有的 `ownedWeapons` 渲染，槽位上限取 5。两点必须一起确认，否则 5 槽会和现有机制打架：

1. `pickupWeapon()`（`src/systems/WeaponManager.ts:382`）目前会在局内把 `ownedWeapons` 从 2 把涨上去。有了固定编队之后，局内拾取到编队外的武器该如何处理（不掉落 / 只补弹 / 临时占第 6 槽）需要在编队文档里定。
2. `keybinds` 缺 `weapon5`（`src/config/keybinds.ts:24` 只到 `weapon4`）。5 槽编队必须补这一项，否则第 5 把枪只能靠滚轮切到。

本规划的验收标准是「给定 N 个槽位（N ≤ 5）能正确排布」，不验收编队的选择流程。

### 5.2 关卡进度条

数据已经就位，不新增系统接口：

```text
进度 = waveIndex / getWaveTotal()
```

`state.waveIndex` 与 `GameScene.getWaveTotal()`（`src/scenes/GameScene.ts:366`）就是现在 `WAVE 3/8` 文本的数据源。需要补的只有两点：

1. **BOSS 刻度**：`getWaveTotal()` 只给总数，判断「最后一波是不是 BOSS」需要读 `LEVELS[].boss` 是否存在。可以由 `GameScene` 再暴露一个 `hasBossWave(): boolean`，或让 `getLevelLabel()` 那一类现有方法附带返回。取哪种在批次 3 实现时定，不影响布局。
2. **无尽模式**：`getWaveTotal()` 返回 `null`，没有分母。此时不画条形，退化为纯计数文本 `WAVE 17`。

### 5.3 刷新时机

进度条只在波次推进时变化，跟随现有的 `EVENTS.waveChanged` 刷新即可，不需要新事件，也不需要每帧更新。


## 6. 响应式重排方案

### 6.1 三层职责

| 层 | 职责 | 触发 |
| --- | --- | --- |
| `Phaser.Game.scale` | 按新视口宽高比 `resize()` 画布，改变逻辑宽度 | `window.resize` / 全屏切换（去抖 ~150ms） |
| 场景摄像机 | 重设 viewport 与 `centerOn`，战场仍锚定 1280×720 中央 | 收到布局变更通知 |
| HUD 容器 | 只移动左右两个根 Container 的 `x`，档位变化时才重建内容 | 收到布局变更通知 |

### 6.2 容器化改造

当前 `LEFT_PANEL_*` / `RIGHT_PANEL_*` 是模块级 `const`，导入时即固化。改造方向：

1. 侧栏内所有对象改为**容器局部坐标**，原点在各自侧栏的内侧上角。
2. 左右各一个根 `Container`，`resize` 时只改这两个容器的 `x`。
3. 布局常量从模块级 `const` 改为按档位返回的工厂函数，只在**档位跨越**时重建内容树。

同档位内的宽度变化只移容器、不重建，因此正在播放的战斗警报、连杀计数、淡入淡出动画不会被打断——这是选这条路线而非 `scene.restart()` 的核心原因。

### 6.3 档位切换时的状态保全

档位跨越（例如 A→C）必须重建内容树。重建前后要保全：

1. 正在显示的战斗警报及其剩余时长。
2. 当前连杀数与里程碑动画。
3. 武器栏在 C 档的自动隐藏计时器状态。
4. 暂停遮罩的可见性与 `pauseReason`。

实现上把这些状态抽成一个可序列化的 HUD 快照，重建后回灌。档位跨越是低频事件，允许一次可见的重排，但不允许丢失警报或让暂停菜单消失。

## 7. 中央浮层处理

四个浮层保留在战场上，不迁入侧栏：

| 浮层 | 位置 | 说明 |
| --- | --- | --- |
| 波次公告 | 战场中央偏上 | 保持现有 y ≈ 126 |
| 战斗警报 | 战场中央偏上，公告下方 | 需要改为**居中**，见下 |
| 连杀里程碑 | 战场中央 | 保持现有 y ≈ 300 |
| 拾取提示 | 战场下方居中 | 保持现状 |

需要修正的一处：战斗警报当前是**左对齐 + 右对齐分列**（`COMBAT_ALERT_LEFT + 22` 起标题、右缘 `-22` 贴副标题，`src/scenes/HUDScene.ts:495-504`），而且横向锚点是为「避开战场内左侧状态板」算出来的。侧栏化之后战场左上不再有面板，这个偏移失去理由。

改为：标题与副标题都以 `GAME_WIDTH / 2` 居中，标题在上、副标题在下两行排布，整块相对战场水平居中。

浮层始终锚定战场坐标（1280×720 中央），不随侧栏宽度变化而位移。

## 8. 实施批次

拆成四批，每批可独立验证与回滚。

### 批次 1 · 布局基础设施

1. `displayLayout.ts` 引入三档枚举与阈值，`resolveDisplayLayout()` 返回档位。
2. `HUDScene` 侧栏内容包进左右两个根 Container，坐标改为容器局部。
3. 布局常量改为按档位返回的工厂函数。

不改任何可见信息，纯结构改造。完成后画面应与当前完全一致。

### 批次 2 · 武器栏常驻与仪表盘分区

1. A / B 档取消武器栏自动隐藏，C 档保留旧行为。
2. 槽位池上限从 8 改为 5，行高放宽到 ~56px，武器图标放大。
3. 第 1 槽（手枪）加不可更换的视觉标记。
4. 按 4.1 / 4.2 落地分区与压缩阶梯；BOSS 区块隐藏时不引起下方上移。

### 批次 3 · 关卡总进度条

1. 右侧栏进度条：`waveIndex / getWaveTotal()`、波次刻度、末端 BOSS 标记。
2. 补一个「本关是否含 BOSS」的只读查询。
3. 无尽模式退化为纯计数文本。

这一批比原计划小得多——不动 `WaveManager`，不加新事件，只消费现有的 `EVENTS.waveChanged`。

### 批次 4 · 响应式与浮层居中

1. `window.resize` / 全屏去抖后 `game.scale.resize()` + 摄像机重设。
2. 同档位移容器、跨档位重建 + HUD 快照回灌。
3. 战斗警报改为居中两行。


## 9. 测试计划

按 `TESTING_RULES.md` 第 5 章决策树，本规划命中第 5 条（HUD、玩家可见画面）与第 4 条（场景创建/销毁、事件监听），最低 V0 + V1 + V3 + V4。批次 3 只读现有波次字段、不改波次生成，因此不触发第 6 条第 8 项的 V5 要求；但进度条要证明「多波推进后仍然正确」，仍应连续打到至少第 3 波。

| 批次 | 最低层级 | 关键验证点 |
| --- | --- | --- |
| 1 | V0 + V1 + V2 + V3 | `display-layout.test.ts` 扩展三档判定；改造前后截图应无差异 |
| 2 | V0 + V3 + V4 | 5 槽常驻、切枪高亮、空弹配色、手枪锁标、BOSS 出现与消失时槽位不跳动 |
| 3 | V0 + V3 + V4 | 进度条随波次单调推进、含 BOSS 关卡末端标记正确、无尽模式退化为文本不越界 |
| 4 | V0 + V3 + V4 | 拖窗口、进出全屏、跨档位重排；重排时正在显示的警报与连杀不丢失 |

`display-layout.test.ts` 是纯函数测试，三档判定与阈值边界（179 / 180 / 259 / 260）应全部覆盖在 V1。

V4 场景按第 11 章矩阵取三个哨兵：第一关、一个 BOSS 关卡、无尽模式。视口至少覆盖 16:9（C 档）、2560×1080（A 档）、以及一个落在 B 档区间的尺寸。

槽位数验证需要人为构造 3 / 4 / 5 槽三种情况。当前可以用 `TESTING_FLAGS.unlockAllWeapons` 拿到满槽，但它给的是 8 把，会超过新的 5 槽上限——这个开关在批次 2 需要一并处理，否则测试路径本身就越界。


## 10. 风险与未决

1. **出战编队未落地，本规划只能做到「按 N 槽排布」。** 5 槽是布局前提，但槽位内容由编队功能决定。编队文档没写之前，武器栏落地后仍然会显示局内拾取来的武器，看起来像编队生效了，实际不是。批次 2 完成时必须明确写清这一点，不能当成编队已实现。
2. **`unlockAllWeapons` 测试开关会给出 8 把武器，超过 5 槽上限。** 这个开关是现在唯一能快速拿到多武器的测试路径，批次 2 必须同时决定它的行为（截断到 5 / 保留 8 并允许溢出显示 / 改为按编队发放），否则测试路径自己就越界。
3. **B 档排版仍可能过密。** 180–260px 要装下 5 个放大的武器槽加关卡情报。5 槽比原来的 8 槽宽裕很多，但行高也从 40px 涨到 56px，净空间不一定变多。压缩阶梯不足时的退路是把武器槽在 B 档收到 ~44px，已写进 4.2。
4. **档位跨越的状态保全成本可能被低估。** HUD 快照需要覆盖的状态比列出的四项更多（例如军械库的 `previousWeaponUsability` 高亮记忆）。若批次 4 发现回灌逻辑过于复杂，退路是「跨档位重建时明确丢弃瞬时浮层，只保全暂停态」，需要时再确认。
5. **`Phaser.Scale.FIT` 改为动态 resize 可能影响渲染倍率。** `DISPLAY_RENDER_SCALE` 同样是模块级一次性计算，动态改变逻辑宽度后文字纹理精度是否需要同步重设，待批次 4 实测。
6. **关卡进度条在无尽模式下没有意义。** 无尽模式没有总波数，退化为纯计数。这等于无尽模式拿不到本规划新增的唯一情报项，右侧栏会比闯关模式空一块。是否给无尽模式换一个替代指标（例如最佳波次对比）留待后续，本规划不做。
7. **主观可读性未验。** 侧栏字号在真实显示设备上是否够读、放大后的武器图标是否清晰、仪表盘信息密度是否过高，属于 V6 真人验收，Agent 不能替代结论。
