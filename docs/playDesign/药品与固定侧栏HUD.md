## 1. 目标

1. 新增三种主动消耗型药品：绷带、急救包、能量饮料。使用需要读条时间，形成「什么时候敢停下来治疗」的战术决策。
2. 药品与现有即时拾取回血并存但分工不同：拾取是战斗中的被动奖励，药品是玩家自己管理的库存资源。
3. 让左右侧栏 HUD **在任何屏幕尺寸下都存在**，不再出现「算出了侧栏空间又丢掉、只剩两条纯色黑边」的现状。
4. 重排侧栏分工：**左＝武器与自身状态，右＝药品与道具信息**，与用户明确要求一致。
5. 修正既有两份文档中「正常屏幕 `sidebarWidth` 恒为 0」的错误结论。

明确不在本轮范围：

1. 药品的局外解锁、等级、改装与专属资源。
2. 除移速外的其它 buff/debuff 框架化（本轮只为能量饮料做单一具名状态）。
3. 队友治疗、复活、部位伤与流血等衍生生存机制。
4. 战前整备页编辑药品配额；本轮携带量走固定初始配额 + 局内掉落。
5. 删除现有 C 档「战场内 HUD」代码路径，理由见 6.4。
6. 自动化测试、类型检查、构建与浏览器实景验收。

## 2. 已锁定决策

以下 8 项由用户在本轮交互中明确选定，实施不得擅自改动：

| 项 | 决策 |
| --- | --- |
| 药品种类 | 绷带 / 急救包 / 能量饮料，三种 |
| 治疗量模型 | 固定点数，接受角色最大生命差异带来的百分比差异 |
| 绷带 | 恢复 30 点，读条 1.5 秒 |
| 急救包 | 恢复 80 点，读条 3.0 秒（绷带的 2 倍） |
| 能量饮料 | 饮用读条 1.0 秒，之后 20 秒内共恢复 60 点，并附带移速提升 |
| 使用中移动 | 可移动，但移速降为 50% |
| 使用中受伤 | **不打断** |
| 使用按键 | 三个独立按键直接使用：`Z` 绷带 / `X` 急救包 / `C` 能量饮料 |
| 侧栏方案 | 方案 D：`sidebarWidth = max(自然算出值, 固定最小值)` |
| 最小侧栏宽度 | 120px（2026-08-19 实施前最终拍板，进入 B 档窄压缩形态） |

### 2.1 本文提议、尚未经用户逐项确认的项

下列条目是为了让规划闭环而给出的默认取值，实施前若用户未反对即按此执行；每项都标了取该值的理由：

| 项 | 提议值 | 理由 |
| --- | --- | --- |
| 移速 buff 幅度 | +20%，持续 20 秒（与 HoT 同步起止） | 与现有濒死移速加成 `1.2` 同量级，不引入第二套数量级 |
| 携带上限 | 绷带 4 / 急救包 2 / 能量饮料 2 | 绷带作为主力续航品给最大量；急救包稀有度体现在上限而非治疗量上 |
| 初始配额 | 绷带 2 / 急救包 1 / 能量饮料 1 | 一局内够做两次小治疗 + 一次大治疗，不足以硬吃 Boss |
| 现有 `type:'health'` 掉落 | **保留不动**，仍即时回 15 点 | 见 4.6 |
| 满血时按键 | 无效，不消耗、不进入读条，只给一次拾取式提示 | 避免误触浪费稀有资源 |
| 重复饮用能量饮料 | 不叠加；刷新为完整 20 秒 / 60 点，未结算的剩余量作废 | 用户未选「可叠加」选项，且叠加需要额外上限约束防无限续命 |
| 主动取消 | 读条期间再次按下同一按键即取消，药品不消耗、已耗时间作废 | 读条最长 3 秒，没有取消手段会变成「按错就等死」 |

## 3. 三种药品数值表

| ID | 名称 | 读条时长 | 治疗结算 | 读条期间等效治疗速率 | 定位 |
| --- | --- | ---: | --- | ---: | --- |
| `bandage` | 绷带 | 1.5s | 读条完成时一次性 +30 | 20 HP/s | 高频小额，波次间隙常规续航 |
| `medkit` | 急救包 | 3.0s | 读条完成时一次性 +80 | 26.7 HP/s | 低频大额，必须找到 3 秒安全窗口 |
| `energy_drink` | 能量饮料 | 1.0s | 读条完成后 20s 内共 +60，速率 3 HP/s | 2.86 HP/s（含读条） | 读条最短，回血最慢，附带机动性 |

三者不是简单的强弱阶梯，而是**「安全窗口长度」与「治疗即时性」的交换**：

1. 绷带读条最短且回血即时，但单次量小于大多数敌人的一次连续输出。
2. 急救包量最大、读条期间等效速率也最高，但需要 3 秒无威胁，实战中通常只能在清空一波后使用。
3. 能量饮料读条只有 1 秒，能在被追击时喝下，代价是治疗分摊到 20 秒；移速 buff 让它成为「边跑边回」的脱战手段，而不是残血救命手段。

## 4. 使用规则

### 4.1 读条状态机

```text
空闲
  -> 按下 Z/X/C 且该药品库存 > 0 且未处于其它读条 且（绷带/急救包时）生命未满
  -> 进入「使用中」：库存立即 -1（防止读条期间重复触发同一件）
       使用中每帧：elapsedMs += delta；移速乘 0.5
       使用中禁止：开火、换弹、切换武器、布置道具
       使用中允许：移动（半速）、被攻击（不打断）、拾取
  -> elapsedMs >= durationMs  -> 结算治疗 -> 回到空闲
  -> 期间再次按下同一按键 -> 取消：库存 +1 回滚，不治疗 -> 回到空闲
  -> 期间玩家死亡 / 战局结束 -> 强制清空，库存不回滚
```

库存在**开始时**扣减而非结算时扣减，是为了避免「按住不放或连点导致一件药品被结算多次」。取消时显式回滚是这个选择的必要配套。

### 4.2 与现有系统的交互边界

| 交互 | 规则 | 依据 |
| --- | --- | --- |
| 移速 | 在 `GameScene.ts:361` 的唯一移速合成点乘算 `0.5` | 该行已是 `moveSpeed * (lowHealth ? 1.2 : 1)` 的单一乘算点，不新增第二处 |
| 濒死加成 | 与濒死 `1.2` 乘算，不互斥 | 濒死时读条移速 = `moveSpeed × 1.2 × 0.5 = 0.6 倍`，仍慢于正常，语义正确 |
| 饮料 buff | 同一乘算点再乘 `1.2`，与濒死可叠乘（最高 `1.44`） | 濒死伤害加成已是独立乘算模式，移速沿用同一约定 |
| 受伤 | 不打断，也不延长；伤害正常结算 | 用户已锁定 |
| 守望者「绝境余生」 | 若读条期间触发保 1 血 + 1.5s 无敌，读条继续 | 该被动不改变输入状态，无需特判 |
| 治疗上限 | 结算时 `min(maxHealth, health + amount)`，超出部分作废、不折算 | 与 `GameScene.ts:1216` 现有即时回血写法一致 |
| 生命小数 | 能量饮料按 `delta` 累加小数并存在累加器中，HUD 显示 `Math.ceil(health)` | 3 HP/s 除不尽帧时长，逐帧取整会累计丢血 |
| 暂停 | 暂停期间 `delta` 不推进，读条与 HoT 自然冻结 | 依赖现有暂停对 `update` 的既有行为 |

### 4.3 能量饮料 HoT 细则

1. 读条 1.0 秒完成的**那一刻**开始 20 秒计时，读条期间不回血、不加移速。
2. 20 秒内匀速回复共 60 点，速率固定 3 HP/s，不受最大生命影响。
3. HoT 期间生命被打到 0 时立即失效，剩余量不保留。
4. HoT 期间再次饮用：先完成 1.0 秒读条，结算时把剩余时间重置为 20 秒、剩余总量重置为 60 点。
5. HoT 期间生命回满：HoT 继续走完计时（因为移速 buff 与之绑定），只是治疗部分不再有效果。

### 4.4 角色差异实测表

用户已确认「固定点数，接受角色差异」。这里把差异写成结论，供后续平衡时直接引用（最大生命取自 `src/config/characters.ts`）：

| 角色 | 最大生命 | 绷带 30 | 急救包 80 | 能量饮料 60 |
| --- | ---: | ---: | ---: | ---: |
| 破阵者 `breacher` | 80 | 37.5% | **100%** | 75.0% |
| 鹰眼 `eagle_eye` | 85 | 35.3% | 94.1% | 70.6% |
| 疾行者 `runner` | 85 | 35.3% | 94.1% | 70.6% |
| 守望者 `watcher` | 105 | 28.6% | 76.2% | 57.1% |
| 堡垒 `bastion` | 140 | 21.4% | 57.1% | 42.9% |

两条必须记住的后果：

1. **破阵者一个急救包等于满血**，这与它 80 生命、120% 伤害的「高风险火力」定位叠加后，会削弱它的风险属性。
2. **堡垒的治疗效率最低**（急救包只回 57%），与 `角色与战前整备系统.md` 风险表里「药品改革时单独校准治疗收益」的预留一致。本轮按固定点数实施，校准留给真人试玩后。

不做百分比治疗的理由：百分比会让堡垒的 140 生命同时获得「更高血量」和「更高单次治疗量」，双重放大生存角色，而这正是既有文档已经点明要避免的方向。

### 4.5 获取方式

1. **初始配额**：`createInitialState()` 里按 2.1 的提议值直接写入，与现有 `items: { mine: 3 }` 同一位置、同一形态。
2. **局内掉落**：在 `DropDef` 已有的 `type:'item'` 之外新增 `type:'medicine'`，携带 `medicineId` 与 `amount`。理由见 8.1——不复用 `type:'item'`，因为拾取分支需要走不同的库存上限与提示颜色。
3. **上限拒收**：库存已达上限时拾取判定返回 `false`，拾取物留在场上，与现有满血时 `type:'health'` 的处理方式一致（`GameScene.ts:1215`）。
4. 本轮不做战前整备页的药品编辑，也不做药品的商店/解锁。

### 4.6 与现有即时回血掉落的关系

**结论：保留 `type:'health'` 即时回 15 点，不改成掉落绷带。**

理由：如果把即时回血改成掉落绷带，玩家在残血被围时捡到的东西从「立刻 +15」变成「需要停下来读条 1.5 秒」，实际是把一个救命道具改成了负担。保留两套治疗的分工反而是清晰的：

| | 触发方式 | 时机成本 | 玩家决策 |
| --- | --- | --- | --- |
| `type:'health'` 拾取 | 走过去自动生效 | 只有移动成本 | 要不要冒险绕路去捡 |
| 三种药品 | 主动按键 + 读条 | 有读条与减速成本 | 现在这个空隙够不够用哪一件 |

代价是项目里存在两个治疗入口，需要在 HUD 上避免混淆：拾取提示继续走现有 `pickupCollected` 浮层，药品状态只在右侧栏，两者不共用视觉。

## 5. 按键

### 5.1 新增动作

`GameAction` 新增三项，`DEFAULT_KEYBINDS` 对应绑定：

| 动作 | 默认键 | 说明 |
| --- | --- | --- |
| `useBandage` | `Z` | 使用绷带 |
| `useMedkit` | `X` | 使用急救包 |
| `useEnergyDrink` | `C` | 饮用能量饮料 |

按键占用现状（`src/config/keybinds.ts`）：`W/A/S/D` 移动、`R` 换弹、`Q` 布置道具、`F` 切换道具、`1`–`5` 武器、鼠标左键开火、滚轮切枪、`ESC` 菜单（固定不可改）。`Z/X/C` 三键当前完全空闲，且在左手 WASD 区正下方，不需要移动手位。

`InputManager` 无需为新动作写特例：`registerKeyboardKeys()`、`repairUnsupportedBindings()`、`pulseForCode()`、`rebind()` 都是遍历 `Object.keys(this.binds)` 的通用实现（`InputManager.ts:65/76/134/180`），新增键位会自动获得注册、修复、改键与冲突交换能力。

### 5.2 三键并排的理由

用户选择三个独立按键而非「切换 + 使用」。这个选择与药品的读条设计是自洽的：读条本身已经要花 1.5–3.0 秒，如果还要先按若干次切换键才能选中目标药品，紧急情况下的总时间成本会翻倍，而三种药品的差异恰恰全部体现在「时间」上。三键直触让「选哪一件」和「花多久」成为同一个决策。

配套要求：三个药品槽在右侧栏必须**常驻可见且位置固定**，包含数量为 0 时也占位。否则按键与视觉位置的对应关系会随库存变化而漂移。

## 6. 固定侧栏：方案 D

### 6.1 现状与根因

> 实施更正：本章 6.2-6.6 的部分推演保留了早期 140px 方案用于追溯。最终实现采用 120px，准确视口数据与连带决策以执行文档 2.1 为准。

现状是：左右两条纯色边一直存在，但它们不是「没有空间」，而是**算出了空间又丢掉**。三步链条已在代码中核对：

1. `DisplayManager.ts:12-15` 把 `window.innerWidth / window.innerHeight`（浏览器视口）而不是显示器分辨率喂给 `resolveDisplayLayout()`。
2. 浏览器 chrome 占掉高度，视口一定比 16:9 更宽。1080p 显示器窗口化实际约 1920×919，宽高比 2.089，代入公式得 `aspectWidth = 720 × 2.0892 = 1504.24`，`sidebarWidth = ceil(112.12) = 113`。
3. `113 < MIN_HUD_SIDEBAR_WIDTH(120)` → 档位 `fallback` → HUDScene 不绘制侧栏，且 GameScene 摄像机视口只有 `GAME_WIDTH` 宽（`DisplayManager.ts:128`），两侧因此直接露出 `main.ts` 的 `backgroundColor: '#111111'`。

即：**只差 7px 就能进入压缩档**，那两条边是被 120 阈值挡在门外的可用空间。

### 6.2 公式改动

`src/ui/displayLayout.ts` 新增一个常量并在 `resolveDisplayLayout()` 里加一次取大：

```ts
/** 侧栏 HUD 的固定最小宽度。用户要求任何屏幕尺寸下左右侧栏都必须存在。 */
export const MIN_FIXED_SIDEBAR_WIDTH = 120;

const naturalSidebarWidth = Math.max(0, Math.ceil((aspectWidth - GAME_WIDTH) / 2));
// 自然黑边够用时直接白拿；不足时加宽逻辑画布，让 FIT 整体等比缩小换出侧栏空间。
const sidebarWidth = Math.max(naturalSidebarWidth, MIN_FIXED_SIDEBAR_WIDTH);
```

关键性质：**中央战场世界始终是完整的 `1280×720`**。关卡配置、敌人生成点、Boss 战场、障碍物坐标、摄像机边界全部零改动，视野零损失。唯一变化的是战场在物理屏幕上显示得多大。

### 6.3 各视口实算落点

按 `resolveDisplayLayout()` + `Phaser.Scale.FIT` 逐个演算，不是估算。`FIT 缩放 = min(视口宽 / 逻辑宽, 视口高 / 720)`，`战场屏宽 = 1280 × FIT 缩放`：

| 视口 | 自然侧栏 | 改后侧栏 | 逻辑宽 | FIT 缩放 | 战场屏宽（改前 → 改后） | 变化 | 侧栏物理宽 |
| --- | ---: | ---: | ---: | ---: | --- | ---: | ---: |
| 1920×1080 全屏 16:9 | 0 | 140 | 1560 | 1.2308 | 1920 → 1575 | −18.0% | 172px |
| 2560×1440 全屏 16:9 | 0 | 140 | 1560 | 1.6410 | 2560 → 2101 | −18.0% | 230px |
| 1920×1200 全屏 16:10 | 0 | 140 | 1560 | 1.2308 | 1920 → 1575 | −18.0% | 172px |
| **1920×919 窗口化（最常见）** | 113 | 140 | 1560 | 1.2308 | 1632 → 1575 | **−3.5%** | 172px |
| 1366×700 小窗口 | 63 | 140 | 1560 | 0.8756 | 1244 → 1121 | −9.9% | 123px |
| 2560×1080 全屏 21:9 | 214 | 214 | 1708 | 1.4988 | 1919 → 1919 | **0%** | 321px |
| 3440×1440 全屏 21:9 | 220 | 220 | 1720 | 1.6744 | 2143 → 2143 | **0%** | 368px |
| 5120×1440 全屏 32:9 | 640 | 640 | 2560 | 2.0000 | 2560 → 2560 | **0%** | 1280px |

三条结论：

1. **超宽屏完全不受影响**，自然侧栏已经大于 140，取大运算不生效。
2. **最常见的窗口化 16:9 只损失 3.5%**，因为那 113px 本来就在空转。
3. **真全屏 16:9 / 16:10 损失 18%**，这是唯一需要用户接受的实质代价。

### 6.4 必须接受的三个副作用

**副作用一：真全屏时出现上下信箱边。** 逻辑画布从 `1280×720`（16:9）变成 `1560×720`（宽高比 2.167），在 16:9 屏幕上 FIT 会以宽度贴边，高度留白。1920×1080 全屏时上下各出现 97px 黑边（总计 194px）；2560×1440 时各 129px。**也就是说：左右黑边被消除，代价是全屏时换来上下黑边。** 这不是缺陷而是几何必然——固定宽度的侧栏必须从某个方向拿走空间。窗口化时视口本身就比 16:9 高得少，上下信箱边只有 33px，几乎不可见。

**副作用二：`fallback` 档位变为不可达。** 取大运算无条件保证 `sidebarWidth ≥ 140 > MIN_HUD_SIDEBAR_WIDTH(120)`，因此 `hudSidebarTier` 只会是 `'compact'` 或 `'full'`，C 档「战场内 HUD」代码路径永不执行。**本轮不删除这段代码**，理由：`HUDScene.ts` 中由 `USE_SIDE_HUD` 分支控制的布局常量有 20 余处（`HUDScene.ts:157-206`），删除是一次纯风险重构，与本轮目标无关。处置方式是在 `displayLayout.ts` 与 `HUDScene.ts` 各写一条中文注释标明该档已不可达、保留原因、以及删除应另开执行文档。

**副作用三：`DISPLAY_RENDER_SCALE` 存在真实回归，必须一并修。** `resolveRenderScale()`（`DisplayManager.ts:21-31`）的水平项分母是 `layout.logicalWidth`：

```ts
const physicalFit = Math.min(
  (window.innerWidth * devicePixelRatio) / layout.logicalWidth,
  (window.innerHeight * devicePixelRatio) / GAME_HEIGHT,
);
return Phaser.Math.Clamp(Math.ceil(physicalFit), 1, MAX_RENDER_SCALE);
```

逻辑宽从 1280 涨到 1560 会把 `physicalFit` 从 `>1` 压到 `≤1`，`Math.ceil` 随之从 2 掉到 1，**文字与 WebGL 缓冲精度直接减半**。触发区间是「16:9 视口且 `视口宽 × dpr` 落在 1281–1560」，例如 1440×810 全屏（dpr 1）：改前 `min(1.125, 1.125) = 1.125 → 倍率 2`，改后 `min(0.923, 1.125) = 0.923 → 倍率 1`。

处置方案：让 `resolveDisplayLayout()` 额外返回 `naturalLogicalWidth = GAME_WIDTH + naturalSidebarWidth * 2`，`resolveRenderScale()` 的水平项改用它作分母。这样「因为强制加宽而多出来的那部分」不参与倍率判定，倍率行为与改动前逐案一致（1440×810 → 2；800×1400 窄高窗口 → 1，仍避免无谓的 2× 缓冲；5120×1440 → 2）。不能简单地只保留垂直项：800×1400 这类窄高视口会因此拿到 2 倍率，白白分配 3120px 宽的缓冲。

### 6.5 面板宽度：140px 落在窄压缩形态，不是宽压缩

必须更正一处我在提问时给出的错误标注。按现有 `resolveSidePanelWidth()`（`HUDScene.ts:144-153`）：

```text
sidebarWidth = 140
  -> panelWidth = clamp(140 - 6, 114, 156) = 134
  -> USE_NARROW_SIDE_HUD = 134 < 140 = true      // HUDScene.ts:160
```

所以 140px 侧栏拿到的是**窄压缩形态**（武器图标 32×20、文字左偏移 50），不是我在选项里写的「宽压缩形态」。这不改变用户已锁定的 140px 决策，但会影响侧栏能装什么。

处置方案：把 `USE_NARROW_SIDE_HUD` 的边界从 `< 140` 调整为 `< 130`，使 134px 面板进入宽压缩形态。核对可行性：宽形态下 `ARSENAL_TEXT_LEFT = 58`，`ARSENAL_SLOT_WIDTH = 134 - 16 = 118`，`ARSENAL_SLOT_TEXT_WIDTH = 118 - 58 - 6 = 54`。54px 足够放 `30/30` 这类弹药文本，且 `fitTextWidth()`（`layout.ts:72`）对超长内容只缩不溢出，因此不存在截断风险。武器图标从 32×20 提升到 40×24，可读性净收益。

### 6.6 小视口下限

侧栏物理宽度 = `140 × FIT 缩放`。要保证物理宽度 ≥ 100px（约等于 14px 字号仍可读的下限），需要 `FIT 缩放 ≥ 0.714`，即**视口宽 ≥ 1120px 且视口高 ≥ 520px**。低于该尺寸时侧栏不会破版，只是与战场一起等比变小；本轮不为其做专门形态，与既有「不为极端屏幕做专门处理」的范围结论一致。

## 7. 侧栏内容重排

### 7.1 与既有 v0.5 规划的冲突及处置

`docs/playDesign/侧栏HUD空间利用.md` §2 锁定的分工是「左＝玩家自身状态（含道具），右＝关卡情报」。用户本轮要求「左侧显示武器，右侧显示药品以及道具的信息」，因此**道具从左侧栏移到右侧栏**，右侧栏由单一职责变为双职责。

新分工：

| | 内容 | 强调色 |
| --- | --- | --- |
| 左侧栏 | 角色与被动 → 生命 → 当前武器与弹药 → 五武器编队栏 | 青色 `0x58c9dd` |

### 7.4 读条呈现位置

读条必须**同时**出现在两处，各自解决不同问题：

1. **右侧栏对应药品槽内**：告诉玩家「在用哪一件、还剩多久」。这是信息主体。
2. **角色脚下战场内的短横条**（宽 40px、高 4px、位于角色下方 22px）：读条期间玩家注意力全部在战场上躲避，视线不会去扫侧栏。这条与现有伤害数字、拾取浮层同属战场内瞬时元素，读条结束立即销毁。

能量饮料的 20 秒 HoT 不占用读条位，改为在该槽的数量位替换为剩余秒数倒数（`20s → 1s`），并让色条呈缓慢呼吸。这样「正在生效」与「正在读条」两种状态在视觉上不会混淆。

移速 buff 不新增独立 UI：它与 HoT 同起同止，倒数秒数已经表达了持续时间。

### 7.5 道具区

道具区保留现有单槽模型（`ItemManager` 目前只有一个 `currentItemId`，`ItemManager.ts` 的 `getOwnedItemIds()` 硬过滤 `category === 'deployable'`），只是从左侧栏移到右侧栏，并补一个标题行与两个按键角标：

```text

│ 道具                          │
├──────────────────────────────┤
│ [Q] 🔵 地雷            ×3    │
└──────────────────────────────┘
```

`[Q]` 为使用（`deployItem`），标题行右端另标注 `[F] 切换`（`nextItem`）。多槽道具区仍是 `侧栏HUD空间利用.md` §11.4 记录的开放问题，本轮不解决——右侧栏剩余 134px 余量不足以容纳多槽道具区，需要先压缩 BOSS 槽或分页，属于另一轮改动。

## 8. 数据与系统边界

### 8.1 药品配置独立成表，不复用 `ItemDef`

**结论：新增 `src/config/medicine.ts`，不给 `ItemDef.category` 加第三个值。**

理由是 `ItemDef`（`types.ts:211-218`）的字段语义全部围绕「场景物 / 玩家布置物」：

```ts
export interface ItemDef {
  id: string;
  name: string;
  category: 'prop' | 'deployable';
  trigger: 'onDamage' | 'onProximity' | 'manual';
  health?: number;       // prop 被打爆所需伤害
  proximity?: number;    // 触发半径(地雷)
  chainable: boolean;    // 是否会被其它爆炸连锁引爆
  ...
}
```

药品没有触发方式、没有被打爆的血量、没有触发半径、不会被连锁引爆。塞进来会产生 4 个对药品永远无意义的可选字段，并且 `ItemManager` 的每一处 `category === 'deployable'` 过滤都要重新审视。独立配置表让两套资源各自保持字段完整性。

```ts
export type MedicineId = 'bandage' | 'medkit' | 'energy_drink';

export interface MedicineDef {
  id: MedicineId;
  name: string;
  /** 读条时长(毫秒)。 */
  useDurationMs: number;
  /** 读条完成时一次性回复的生命；能量饮料为 0。 */
  instantHeal: number;
  /** 持续回复总量与持续时长；非持续型两者为 0。 */
  overTimeHeal: number;
  overTimeDurationMs: number;
  /** 持续期间的移速倍率；无加成为 1。 */
  overTimeMoveSpeedMultiplier: number;
  /** 携带上限。 */
  carryMax: number;
  /** 侧栏色条与提示色。 */
  color: number;
}
```

字段名全部在本文确认，实施时不得改名或增补猜测字段。

### 8.2 `PlayerState` 新增字段

`src/systems/GameState.ts` 的 `PlayerState` 追加三项，与现有 `items` / `currentItemId` 并列：

```ts
/** 药品库存：id -> 数量。 */
medicines: Record<MedicineId, number>;
/** 正在进行的读条；空闲为 null。 */
medicineUse: { medicineId: MedicineId; elapsedMs: number; durationMs: number } | null;
/** 能量饮料持续效果；未生效为 null。healCarry 存放未满 1 点的小数余量。 */
overTimeHeal: { remainingMs: number; healPerMs: number; healCarry: number; moveSpeedMultiplier: number } | null;
```

`createInitialState()` 在现有 `items: { mine: 3 }` 同一位置写入初始配额：`medicines: { bandage: 2, medkit: 1, energy_drink: 1 }`，`medicineUse: null`，`overTimeHeal: null`。

### 8.3 `MedicineManager` 职责

新增 `src/systems/MedicineManager.ts`，形态对齐现有 `ItemManager`（构造时接 `scene / state / input`，对外暴露 `update(delta)`）：

| 方法 | 职责 |
| --- | --- |
| `update(delta)` | 读三个按键的 `justPressed`；推进读条与 HoT；结算治疗 |
| `addMedicine(id, amount): number` | 受 `carryMax` 约束，返回实际入库量；供拾取调用 |
| `getMoveSpeedMultiplier(): number` | 返回 `读条中 ? 0.5 : 1` 与 `HoT 中 ? 1.2 : 1` 的乘积 |
| `cancelUse()` | 主动取消，回滚库存 |
| `clearOnDeath()` | 死亡/战局结束时清空读条与 HoT，不回滚库存 |
| `isChanneling(): boolean` | 供 `GameScene` 封锁开火/换弹/切枪 |

`getMoveSpeedMultiplier()` 的返回值接入 `GameScene.ts:361` 这一唯一移速合成点：

```ts
// 改后：濒死加成、读条减速、饮料加速在同一处乘算，不新增第二个移速来源
this.player.update(
  this.inputManager,
  this.state.player.moveSpeed * (lowHealth ? 1.2 : 1) * this.medicineManager.getMoveSpeedMultiplier(),
);
```

### 8.4 事件

`src/constants.ts` 的 `EVENTS` 只新增一项：

```ts
medicineChanged: 'medicineChanged',
```

用于库存变化、读条开始/结束、HoT 开始/结束这五种离散变化。**读条进度与 HoT 倒数不走事件**：`HUDScene` 已有 `update(time)` 且持有 `gameScene` 引用，逐帧读 `gameScene.state.player.medicineUse / overTimeHeal` 即可，避免每帧发事件。治疗结算仍复用现有 `EVENTS.healthChanged`。

### 8.5 掉落

`DropDef`（`types.ts:131-135`）新增一种：

```ts
export type DropDef = AmmoDropDef | (DropBase & {
  type: 'weapon' | 'item' | 'health' | 'enhancement_pack';
  itemId?: string;
  amount?: number;
}) | (DropBase & {
  type: 'medicine';
  medicineId: MedicineId;
  amount: number;

```

`GameScene.applyPickup()` 增加一个分支，位置紧跟现有 `type === 'health'` 分支之后（`GameScene.ts:1214`），形态对齐 `type === 'item'` 分支：库存满则返回 `false` 让拾取物留在场上，成功则发 `pickupCollected` 浮层并播 `pickup` 音效。

具体掉落概率与投放到哪些僵尸的 `drops` 表上，本轮不定；需要与波次节奏一起调，属于平衡工作而非结构工作。

### 8.6 存档

**不新增存档字段。** 药品是纯局内资源：初始配额写死在 `createInitialState()`，局内靠掉落补充，结算时归零。因此 `CURRENT_SAVE_VERSION` 保持 5，无需迁移。

例外是键位：`Z/X/C` 通过 `DEFAULT_KEYBINDS` 进入既有的 `SAVE_KEYS.keybinds`。旧存档的 keybinds 对象缺少这三个动作，读取后 `this.binds.useBandage` 为 `undefined`。`repairUnsupportedBindings()`（`InputManager.ts:74-85`）遍历的是 `Object.keys(DEFAULT_KEYBINDS)`，会检出 `undefined` 不受支持并回填默认值——**旧存档因此自动获得三个新键位，无需写迁移代码**。实施时须核对该函数对 `undefined` 的 `code.startsWith(...)` 调用不会抛异常，必要时补一个类型守卫。

## 10. 风险与优化方案

| 风险 | 影响 | 优化方案 |
| --- | --- | --- |
| 真全屏 16:9 战场缩小 18% 并出现 194px 上下信箱边 | 全屏玩家观感变差，可能觉得「画面变小了」 | 已向用户明示并锁定。若试玩后不可接受，回退路径是把 `MIN_FIXED_SIDEBAR_WIDTH` 降到 120（损失 15.6%）或做全屏专属的半透明浮层形态 |
| `DISPLAY_RENDER_SCALE` 由 2 掉到 1 | 1281–1560px 宽视口文字变模糊 | 6.4 副作用三的 `naturalLogicalWidth` 方案，倍率行为逐案与改前一致 |
| 受伤不打断 + 可移动，读条几乎无风险 | 急救包 3 秒读条形同免费，80 点大额回血失去代价 | 代价已改由「移速减半 + 禁止开火」承担：3 秒不能还击且跑不动，在密集波次里是实质风险。若试玩后仍过强，优先调 `carryMax` 与掉落率，不动读条规则（用户已锁定） |
| 破阵者一个急救包满血 | 80 生命的高风险角色失去脆弱性 | 本轮接受（用户已锁定固定点数）。校准手段留给携带上限：可单独给破阵者更低的急救包上限，而不改治疗量 |
| 堡垒治疗效率仅 57% | 生存角色反而最缺治疗 | 与既有文档预留一致，留给真人试玩。备选是给堡垒更高的初始配额 |
| 库存在读条开始时扣减 | 取消或异常中断时若忘记回滚，药品会凭空消失 | 回滚只有一个出口（`cancelUse()`），死亡路径明确不回滚；两条路径都必须有定向测试 |
| 三键新增占用 Z/X/C | 未来若需要闪避、互动等动作将无键可用 | 当前空闲键仅剩 `E/G/V/Tab/空格`，本轮消耗 3 个后仍有余量；记录该事实，后续新动作优先考虑 `空格/E` |
| `fallback` 档位代码变死代码 | 后续维护者不知道该分支永不执行，白花时间维护 | 在 `displayLayout.ts` 与 `HUDScene.ts` 各写一条注释标明不可达、保留原因与删除前置条件 |
| 右侧栏承担双职责后余量仅 134px | 未来加任何右侧信息都会溢出 | 已把余量写进 7.2；下一次扩展必须先压缩 BOSS 槽或引入分页，不得靠缩字号硬塞 |
| 生命值出现小数 | 结算界面或对比判断出现 `99.7 / 100` 之类显示 | `overTimeHeal.healCarry` 只累加小数，写回 `health` 时取整；HUD 统一 `Math.ceil` |
| 能量饮料移速 buff 与濒死叠乘到 1.44 | 残血 + 饮料的疾行者移速达 145 × 1.44 ≈ 209 px/s，可能完全脱离僵尸 | 记录为待观测项。若确认过强，改为 `Math.max` 取最大而非乘算，只改 `getMoveSpeedMultiplier()` 一处 |

## 13. 对既有文档的更正

本轮核查发现两份已锁定文档存在同一个事实性错误，已同步更正：

1. `docs/playDesign/侧栏HUD空间利用.md` §2.1 的落点表与其后「全部正常屏幕的 `sidebarWidth` 都是 0」的结论。
2. `docs/execution/2026-08-18-hud-viewport-scope.md` §2 的同源推算。

错误成因：两处都按**显示器分辨率**代入 `resolveDisplayLayout()`，但 `DisplayManager.ts:12-15` 实际喂入的是 `window.innerWidth / window.innerHeight`。浏览器 chrome 占掉高度后视口一定比 16:9 更宽，因此窗口化的 1080p 显示器算出的是 `sidebarWidth = 113`，不是 0。「`sidebarWidth` 恒为 0」只在**真全屏**下成立。

该错误的实际后果就是本文要解决的现象：那两条一直存在的边不是「没有空间」，而是 113px 的可用空间被 120 阈值挡在门外。
