# 2026-08-22 拾取强化包后整局卡死

> 状态：已修复并通过实景验证
> 影响范围：所有会掉强化包的关卡与无尽模式，敌群越密越容易触发
> 涉及文件：`src/scenes/HUDScene.ts`、`src/scenes/GameScene.ts`

## 1. 症状

战斗中走到强化包上，整局彻底卡死：

- 战场完全静止（感染体、子弹都不动）。
- **抽卡界面不出现**，屏幕上没有任何新界面。
- **强化包还留在地上**，没有被消耗。
- HUD 正常显示（生命、武器、负重都还在），但一切都停住了。
- 按任何键都没反应，只能刷新页面，这一局的进度全部丢失。

用户提供的现场截图：第十关 WAVE 2/6，HUD 右下角显示 `连杀 ×4`，
玩家脚下压着一个标着「强化」的掉落物。**`连杀 ×4` 是关键线索**（见第 4 节）。

## 2. 判据

```js
// 卡死 = 冻结在抽卡状态，但没有任何可交互的抽卡界面
scene.pauseReason === 'cardSelection'
  && (!game.scene.isActive('CardSelectionScene')
      || game.scene.getScene('CardSelectionScene').children.list.length === 0)
```

为什么这个条件等于「永久卡死」：`pauseReason` 只有在 `CARD_SELECTED_EVENT`
事件里才会被清掉（`GameScene.handleCardSelected`），而**只有 `CardSelectionScene`
会发这个事件**。抽卡场景不存在 → 这把锁永远没人能解开。

## 3. 排查过程

按时间顺序，包含走错的方向。

### 3.1 先读代码，列出候选（全部错了）

读了 `CardSelectionScene`、`GameScene.handleEnhancementPickup`、
`handleWaveRewards`、`WaveManager` 的奖励状态机，提出四个假设：

| 假设 | 排除依据 |
| --- | --- |
| `scene.stop()` 是入队执行，紧接着的拾取会走 `restart` 分支把场景搞坏 | 写探针在同一次调用栈里「结算 + 立刻再拾取」，`restart` 分支正常出卡，未复现 |
| 卡池抽空时弹出空界面且无法退出 | 代码已有 `drawnCards.length === 0` 分支，实测走「暂无可用增强」并正常消耗，未复现 |
| 某张强化卡在 `create()` 阶段抛异常（`getEnhancementWeaponLabel` 会 throw） | 逐张把 33 张卡单独送进 `create()`，全部通过，无一抛出 |
| `shuffled()` 死循环导致浏览器挂起 | 读 `utils/math.ts`，标准 Fisher-Yates，无死循环 |

**教训**：这四个假设都是「读代码想出来的」，一个都没中。真正定位靠的是下一步。

### 3.2 转向真实链路复现

前面的探针都在直接调 `handleEnhancementPickup()`，绕过了真实的
「物理碰撞回调 → `applyPickup`」路径，也把 `waveManager.state` 强设成 `complete`
从而屏蔽了波次推进。改成完全真实的长局压测：

- `TESTING_FLAGS.enhancementDropChance = 1`，让每只感染体必掉强化包（走正式掉落系统）。
- 用 `damageZombie` 真实击杀，靠真实碰撞回调拾取，用真实按键 `1` 选卡。
- 每 tick 轮询第 2 节的判据，连续 220 tick。

**第一次跑没复现**，但暴露了探针自己的问题：它每 tick 都往 `drops[0]` 走，
而 `drops[0]` 是个捡不起来的掉落物（`applyPickup` 对非 fixed 弹药 `return false`，
掉落物不despawn），玩家被永远钉在那儿，压根没碰到强化包
（现象：`enh=0`、掉落物堆积到 37 个、抽卡界面一次都没开）。

改成只追 `drop.type === 'enhancement_pack'` 后，**第 218 tick 复现**，
并且拿到了完整堆栈。

### 3.3 堆栈直接指向根因

```
TypeError: Cannot read properties of null (reading 'onPause')
    at Tween.dispatchEvent (phaser)
    at Tween.pause (phaser)
    at HUDScene.syncPauseOverlay
    at EventEmitter.emit
    at GameScene.setPause
    at GameScene.handleEnhancementPickup
    at GameScene.applyPickup
    at World.collideSpriteVsSprite     ← 在物理步进内部
```

### 3.4 确认是哪一个补间

`syncPauseOverlay` 对五个缓存补间字段调用 `pause()`。逐个查它们的清理约定：

| 字段 | 播完后是否自清 |
| --- | --- |
| `announcementTween` | ✅ `onComplete` 里置 null |
| `combatAlertTween` | ✅ |
| `pickupToastTween` | ✅ |
| `milestoneTween` | ✅ |
| **`killStreakTween`** | ❌ **没有 `onComplete`** |

`showKillStreak` 建的是一条 **150ms** 的缩放补间，播完不归还引用。
于是连杀期间这个字段几乎一直指着一具已被 Phaser 销毁的补间——
正好对上截图里的 `连杀 ×4`。

## 4. 根因

完整因果链：

1. 玩家连杀 ≥2 → `showKillStreak` 建一条 150ms 补间存进 `this.killStreakTween`。
2. 150ms 后补间播完，Phaser 把它移出 TweenManager 并清掉内部引用。
   **`this.killStreakTween` 仍指向这具尸体**（没有 `onComplete` 归还引用）。
3. 玩家踩到强化包 → 物理碰撞回调 → `applyPickup` → `handleEnhancementPickup`
   → `scene.launch('CardSelectionScene')`（**Phaser 里是入队，不是立即执行**）
   → `setPause('cardSelection')`。
4. `setPause` 发 `pauseChanged` → `HUDScene.syncPauseOverlay`
   → `this.killStreakTween?.pause()`。`?.` 只防 null，防不住「已销毁」
   → Phaser 在派发 `onPause` 时读到 null → **TypeError**。
5. 异常从 `setPause` 逃出，沿着物理碰撞回调一路上抛，**打断整个游戏步进**，
   于是第 3 步排队的 `scene.launch` 永远没被 SceneManager 处理。
6. 留下的状态：`pauseReason = 'cardSelection'`、物理已暂停、`timeScale = 0`、
   **抽卡场景不存在**。而只有抽卡场景能解冻 → 永久卡死。
   `applyPickup` 也没能返回 true，所以**强化包留在地上**——与截图完全一致。

为什么「敌群越密越容易触发」：连杀窗口几乎总是新鲜的，
所以战斗中的每次强化包拾取几乎都会踩中。

## 5. 修复

三层，每层解决不同的问题。**只做第一层也能修掉当前故障，
后两层是为了让同类故障不再表现为「丢掉整局」。**

### 第一层：根因 —— 不对已销毁的补间调用 pause/resume

`src/scenes/HUDScene.ts`

- 新增模块级 `setTweenPaused(tween, paused)`：先做存活判定再操作，
  失效则返回 null 让调用方清空字段。判定口径**复用本文件既有的
  `getTweenRemaining`**：`!tween.isPlaying() && !tween.isPaused()` 即已失效。
- `syncPauseOverlay` 改为调用 `setBroadcastTweensPaused(paused)`，统一处理五个字段，
  以后新增播报补间也自动被覆盖。
- `showKillStreak` 补上 `onComplete` 归还引用，与另外四条对齐。

### 第二层：隔离 —— 表现层异常不得打断冻结状态机

`src/scenes/GameScene.ts` `setPause()`

`pauseChanged` 的订阅方是 HUD，属表现层；冻结状态机属核心正确性。
把 emit 包进 `try/catch`，异常记 `console.error` 后继续。
**这里换取的是「HUD 画不出来」而不是「整局卡死」**，异常本身不被静默。

### 第三层：看门狗 —— 冻结必须有对应界面

`src/scenes/GameScene.ts` 新增 `watchdogCardSelection()`，在 `update()` 的
暂停早退分支里每帧检查一条不变量：
`pauseReason === 'cardSelection'` 时抽卡场景必须存在。

`scene.launch` 入队需要一两帧才生效，所以给 1500ms 宽限
（`CARD_SELECTION_LAUNCH_GRACE_MS`，用 `game.loop.time` 计时，
因为冻结期间 `timeScale = 0`、场景计时器不累计）。超时则走
`handleCardSelected(null)` 按「跳过本次强化」收场，并给玩家一条提示。

**代价明确**：宁可损失一张强化卡，不能让玩家丢掉整局。
它不关心为什么没起来，只守不变量，所以对未来的未知原因同样有效。

## 6. 验证

Chrome `151` headless + CDP，第十关，6 把武器编队，
探针 `.debug-cardlock-*.mjs`，证据 `.debug-cardlock-evidence/`。

| 项 | 结果 |
| --- | --- |
| V1 根因：连杀补间播完后 `setPause` | 字段已自清为 null，`setPause` 不再抛异常 |
| V2 隔离：故意让 `syncPauseOverlay` 抛异常 | 拾取流程不再中断，抽卡界面照常出现（12 个子对象） |
| V3 看门狗：把 `scene.launch` 打成空操作 | 1560ms 自愈，`pauseReason` 回到 null，未永久冻结 |
| V4 真实长局 ×3（各 220 tick） | 全部 `no deadlock`，运行时异常 0 条，正常吃到 4 张强化 |
| `npm run typecheck` | 未新增错误（仍是 26 个既有错误） |

**修复前的对照**：同一个 V4 探针在修复前于第 218 tick 复现，
`pauseReason='cardSelection'` 且 `cardActive=false / children=0`，
并抛出第 3.3 节的 TypeError。

## 7. 失效信号

出现以下任一现象，说明本文档的方案对新故障无效，**不要在原方案上打补丁**：

1. 又出现「战场冻结 + 无抽卡界面」，但**超过 1500ms 没有自愈**
   → 第三层看门狗没生效。可能 `update()` 没被调用（整个游戏循环挂了，
   属真正的 JS 死循环，与本文故障不同类），或 `pauseReason` 是别的值。
2. 自愈提示「强化界面异常 · 已跳过」**频繁出现**
   → 说明第一、二层没挡住真正的异常，看门狗在反复兜底。
   去 console 找被 `console.error` 记下来的原始异常，那才是新根因。
3. 冻结时 `pauseReason` 是 `'menu'` 而不是 `'cardSelection'`
   → 与本故障无关，是暂停菜单的问题。
4. 卡死发生在**没有连杀**、也没有任何强化包的场合
   → 触发路径不同，本文档的根因不适用。

## 8. 顺带发现（未在本轮修复）

`GameScene.applyPickup` 对 `ammoMode !== 'fixed'` 的弹药掉落 `return false`，
调用方因此不 despawn，掉落物会一直留在地上直到自然过期。
排查时它把探针里的玩家钉在原地整整 220 tick。
正常链路里 `spawnDrops` 会先把自适应弹药解析成 fixed，所以实机大概不可达，
但「返回 false 就永久留在场上」这个约定本身很容易再次咬人。属独立问题，未改。
